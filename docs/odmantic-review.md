## Summary

Вопрос "брать ли ODMantic в 007" не стоит: в дереве нет ни MongoDB, ни
Pydantic, ни Python-сервиса, который мог бы его импортировать. Реальный
предмет — четыре решения из его устройства.

Само состояние проекта на дату этого документа: **релиз заморожен, ветка
заморожена, выход с Motor начат в коде и не доведён до упаковки**. Как
фундамент для нового production-ядра — нет. Как источник идей — да, и
конкретно одна из них (парность sync/async) ложится на правило 1
`docs/evidence-and-decision-discipline.md` как готовый отрицательный пример.

### Три поправки к исходной оценке

1. **"118 открытых issues" — это issues + PR.** На странице репозитория
   2026-08-06: **87 open issues и 31 open PR**. 118 — это
   `open_issues_count` из GitHub API, который считает PR как issues. Сумма
   сходится точно, так что это не расхождение в данных, а склейка двух
   разных величин. Картина от этого не мягче (хвост в 87 issues остаётся
   хвостом), но цифру надо называть правильно.

2. **Звёзды.** Страница показывает "1.2k"; точное число не зафиксировано —
   `api.github.com` отдаёт 403 через прокси этой сессии. Порядок величины
   ("~1.2k") — единственное, что здесь обосновано.

3. **Выход с Motor уже начат в коде — и упаковка за ним не пошла.** Это
   существеннее, чем "зависимость просто есть".

   ```text
   Артефакт говорит:  odmantic/engine.py:42-53 — импорт motor обёрнут в
                      try/except ImportError, при неудаче `motor = None`;
                      engine.py:319-322 — AIOEngine падает с RuntimeError и
                      подсказкой `pip install "odmantic[motor]"`;
                      tests/integration/test_engine.py:45 —
                      test_no_motor_passes_with_syncengine_client_creation
                      фиксирует, что SyncEngine работает при `motor = None`.
                      При этом pyproject.toml:46-76 объявляет extras
                      test/fastapi/doc/lint/dev — extra `motor` там нет, и в
                      метаданных PyPI 1.1.0 его тоже нет.
   Вывод:             синхронный путь от Motor уже отвязан, а подсказка
                      `odmantic[motor]` на 1.1.0 недостижима — она указывает
                      на несуществующий extra. Подготовка к развязке сделана
                      на уровне импортов и остановилась до упаковки; async-путь
                      backend'а на PyMongo Async по-прежнему не имеет.
   ```

   То есть таймер на несущей стене — да, но стена уже частично разобрана, и
   работа встала ровно там, где её видно снаружи.

## Что стоит забрать

Ни одна из этих идей не требует ни MongoDB, ни Python.

**1. Типизированный DSL запросов через перегруженные операторы.**
`odmantic/field.py:328-408` — класс `FieldProxy` определяет `__gt__`, `__ge__`,
`__lt__`, `__le__`, `__eq__`, `__ne__`, каждый из которых возвращает не `bool`,
а `QueryExpression` (`odmantic/query.py:9`, подкласс `Dict[str, Any]`).
Композиция — через `__and__`/`__or__` на самом выражении. Итог: выражение
фильтра — обычное значение, которое можно построить, передать и проверить, а
не строка. Для "007" ближайший аналог — селекторы контекста
(`research/b1-context/schema/selector-v0.schema.json`): там та же задача
"выражение отбора как проверяемое значение", решённая через схему, а не через
язык хоста.

**2. Разделение модель / сериализация / engine.** Три слоя лежат в трёх файлах
(`model.py` 1047 строк, `bson.py` 437, `engine.py` 1110), и engine ничего не
знает о валидации: `BaseEngine._build_query` (`engine.py:181`) принимает уже
готовые `QueryExpression`. Граница проведена по данным, а не по удобству.

**3. Отслеживание изменённых полей перед записью.** `model.py:545` —
`__slots__ = ("__fields_modified__",)`, наполняется в `__setattr__`
(`model.py:711,715`); `engine.py:522` берёт
`instance.__fields_modified__ | instance.__mutable_fields__` и пишет только
их, а после успешной записи сбрасывает множество (`engine.py:535`). Дешёвый
приём: единица записи — дельта, а не документ.

**4. Общий контракт для sync/async — как отрицательный пример.** Вот это
интереснее всего, и ровно не в ту сторону, в какую хочется.

```text
Артефакт говорит:  engine.py:157 — BaseEngine держит общую часть (построение
                   запроса, cascade-pipeline); AIOEngine (engine.py:295) и
                   SyncEngine (engine.py:715) реализуют публичные методы
                   раздельно. В tests/integration/test_engine.py — 111 тестовых
                   функций, из них 53 с именем `test_sync_X`, и для каждой из
                   53 существует парная `async def test_X` (совпадение 53 из 53).
Вывод:             две проекции одной семантики удерживаются в согласии
                   вручную — общим query-builder'ом и зеркальным корпусом
                   тестов, написанным дважды. Общего канонического описания
                   поведения, из которого выводились бы обе проекции, нет;
                   зеркальность корпуса ничем не проверяется, кроме
                   дисциплины автора.
Отношение к 007:   это ровно тот разрыв, который описывает правило 1
                   (projection-bound contracts) в
                   docs/evidence-and-decision-discipline.md: Authority и
                   Projection есть, Conformance — дублирование, а не общий
                   корпус, Evidence отсутствует. Полезно как готовый
                   counterexample для MG-C, а не как образец для копирования.
```

## Вердикт для 007

**Как зависимость — вопрос не стоит.** Поиск по дереву на 2026-08-06 не
находит ни одного файла, упоминающего `mongo`, `pydantic` или `odmantic`;
ядро — Rust, а весь Python в репозитории — это 27 файлов: 26 в
`research/b1-context/tools` (хранилище content-addressed и файловое —
`o7b1/cas.py`, `o7b1/canonical.py`) плюс `tools/verify_qodec_cleanup_record.py`.
Никакой миграции здесь нет и вводить document store не за чем.

**Как источник идей — берём пункты 1–4 выше**, с оговоркой, что пункт 4 —
предупреждение, а не образец.

**Если Python-сервису из окружения "007" когда-нибудь понадобится MongoDB** —
на дату этого документа брать ODMantic не следует, и причина не в качестве
API: `master` стоит с 2026-01-25, релиз один и почти пустой, поддержка
Python 3.13/3.14 лежит в draft-PR того же дня, а объявленная зависимость от
Motor переживёт дату deprecation (2026-05-14, уже прошедшую) с критическими
фиксами лишь до 2027-05-14. Прямой PyMongo Async — более короткий путь;
сравнение с активно поддерживаемыми ODM (Beanie и другие) в рамках этого
обзора не проводилось и остаётся открытым.

Для прототипа на Python 3.12 — годится: API чистый, кода нужно мало.
Прототип и не переживает дату EOL.
