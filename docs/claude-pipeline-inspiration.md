# claude-pipeline: что переносить в 007, а что оставить автору

- **Status:** review / inspiration note (не план работ, не принятое направление)
- **Scope:** `o7` run/gate/verdict, run record, будущий autonomy controller
- **Date:** 2026-08-06
- **Source:** [stevegrocott/claude-pipeline](https://github.com/stevegrocott/claude-pipeline),
  ревизия `23e402b` (`chore(plugin): bump pipeline-core to 0.8.1 (#780)`,
  2026-08-05), shallow clone `main`
- **Intent:** зафиксировать, какие протоколы и policy-паттерны из
  `claude-pipeline` стоит утащить в 007, отделив проверенные факты об исходнике
  от выводов на их основе (`docs/evidence-and-decision-discipline.md`, правило 4).

## Summary

`claude-pipeline` — issue-driven конвейер разработки для Claude Code:
`/explore "идея"` исследует репозиторий и создаёт GitHub issue, `/implement-issue
42 main` читает issue, извлекает задачи, реализует, гоняет проверки, создаёт PR и
проводит ревью. Issue — единственный источник истины.

Полезен он не структурой (двухфазный конвейер — очевидность), а тремя вещами,
которых в большинстве «agent pipeline» репозиториев нет:

1. результат стадии — типизированный envelope, а не exit code и свободный текст;
2. агентское `passed` не принимается на веру, а сверяется с его же счётчиками;
3. есть состояние «не измерено», отдельное от «прошло» и «упало».

Третий пункт — это ровно `ERROR` из правила 2 `AGENTS.md`, только на уровне
тестовой стадии, а не всего прогона. Это и есть главная причина смотреть на этот
репозиторий.

Брать его как основу не стоит: реализация — Bash-государство, и оно уже ломалось
об собственный размер (см. «Где начинается Bash-цирк»).

## Что переносить

Порядок — по убыванию ценности для 007.

### 1. `unmeasured` как отдельное состояние тестовой стадии

`AGENTS.md`, правило 2, уже фиксирует, что `ERROR` — это «харнесс не смог
получить достоверный ответ», и что схлопывание `ERROR` в соседа превращает
сломанный харнесс в зелёный прогон. Чего у 007 нет — так это **механизма**,
который ловит этот случай на уровне отдельного гейта.

У них он есть и он дешёвый: вердикт стадии проверяется против её собственных
счётчиков.

```text
verdict = passed, tests_failed > 0            ->  failed
verdict = *,      passed + failed < run       ->  unmeasured
любой счётчик не число ("unknown", пусто)     ->  unmeasured
unmeasured                                     ->  НЕ провал, но и НЕ успех:
                                                   отдельный degraded-маркер
```

Прямой аналог для 007: гейт, который отчитался об успехе, но не предъявил
измерения, обязан давать `ERROR`, а не `PASS`. Сейчас `src/gate.rs` запускает
`bash -lc` и читает exit code — то есть ровно тот сигнал, который
`docs/evidence-and-decision-discipline.md` приводит первым примером
«сигнал нижнего слоя ≠ факт верхнего слоя».

Это не новая архитектура, а конкретный оракул для уже принятого правила.

### 2. Stage-result envelope и единственная точка диспетчеризации

Стадия возвращает JSON-envelope. Одна функция (`_apply_stage_action`) выбирает
одно из четырёх действий: `accept`, `bail`, `escalate`, `retry_same`. Сырые exit
codes и произвольный текст агента не разбираются в каждом месте вызова
отдельно.

Это тот же трёхслойный контур, который `docs/evidence-and-decision-discipline.md`
рисует как cross-cutting constraint:

```text
raw representation / transport signal
        │  authority-specific classifier
        ▼
typed semantic fact
        │  deterministic policy
        ▼
decision or admissible transition
```

Их envelope — это средний слой, а `_apply_stage_action` — нижний. Для 007
осмысленно расширить его до того, что у нас уже есть в словаре:

```text
stage result
  verdict            PASS | FAIL | ERROR
  evidence refs      пути в run record, а не пересказ
  failure class      классификация authority-адаптером
  retryability
  changed assumptions
  next permitted actions
```

`evidence refs` и `failure class` — наша добавка; у них envelope несёт вердикт,
но не обязан предъявлять артефакт, на котором вердикт стоит.

### 3. Issue/task contract как исполняемый контракт

Их формат задачи одновременно читается человеком, парсится оркестратором,
задаёт scope, привязывает задачу к роли агента и даёт критерий остановки:

```text
- [ ] `[agent-name]` **(M)** Task description. Scope: 2 files. Done when: [criterion].
```

Ценно здесь не разметка, а то, что `Done when:` — обязательное поле. Задача без
критерия остановки не парсится.

Для 007 это ложится на `TaskContract` из
`docs/agentic-coding-discipline-proposal.md`, но нужны наши поля: `task_id`,
`depends_on`, `affected_files`, `acceptance_criteria`, **`evidence_required`**,
`status`. Последнее — то, чего у них нет: контракт называет, чем задача
считается закрытой, но не называет, какой артефакт это доказывает.

### 4. Бюджеты как терминальное состояние, а не как предупреждение

Мягкий порог (80 % потолка) предупреждает; жёсткий завершает прогон состоянием
`budget_exceeded`, которое **никогда не эскалируется и не ретраится**. Плюс
потолок числа эскалаций (5) и глобальный wall-clock.

Важна именно терминальность. Бюджет, из которого можно выйти эскалацией, —
это не бюджет.

### 5. Разделение reusable core и project-owned configuration

Плагин поставляет скрипты, схемы, hooks и skills; проект сохраняет
`.claude/config/platform.sh`, `.claude/config/context.md` и `.claude/agents/*.md`.
Бандл — явный allowlist, и забытый в нём файл роняет тест, а не тихо не доезжает
до потребителя.

Для нас это модель общего слоя между 007, Qodec и остальным: обновление ядра не
перетирает проектные настройки, а список того, что вообще едет, проверяется
машиной.

## Второй эшелон

Забирать при необходимости, не как обязательное:

- роутинг моделей по сложности задачи и типу стадии, с явной цепочкой эскалации;
- параллелизм **только** при доказанном отсутствии пересечения файлов;
- автоматическое создание follow-up issue из замечаний ревью
  (`scripts/create-followup-issue.sh`);
- resume из явно сохранённого состояния (`status.json`), а не из пересказа
  модели.

## Где начинается Bash-цирк

Конвейер обрабатывал issue, которое меняло сам `batch-orchestrator.sh`. После
merge bash продолжал читать уже переписанный файл с прежнего byte offset и падал
с синтаксической ошибкой: работа выполнена, PR смержен, `status.json` остался в
состоянии `running`.

Фикс — запуск из приватной `mktemp`-копии с re-exec. Изобретательно, покрыто
тестами, и уже стоит в обоих оркестраторах. Но диагноз от этого не меняется:
система настолько связана с собственным исполняемым файлом, что обновление
оркестратора ломает запущенный оркестратор.

Это ровно тот класс отказа, ради которого 007 держит run record отдельным
каноническим артефактом (`AGENTS.md`, правило 3): «частично упавший прогон не
должен оставлять запись, которая читается как завершённая». Здесь прогон оставил
запись, которая читается как *идущая*, — тот же дефект с другого конца.

## Что не переносить

- **Bash как язык оркестрации.** 12 104 + 2404 строки top-level Bash. Втащить
  это в 007 было бы не интеграцией, а усыновлением чужого технического долга.
  Наш эквивалент — типизированное ядро на Rust, Bash остаётся тонким launcher-слоем.
- **Конвейер целиком.** Двухфазный explore→implement — не та часть, которой этот
  репозиторий ценен.
- **Версию манифеста как идентичность артефакта.** См. `0.8.0` → `0.8.1`.

## Открытые вопросы

- Число коммитов расхождения с `aaddrick/claude-pipeline` и дата остановки
  оригинала не проверены (GitHub API недоступен для неприкреплённого репозитория,
  клон shallow). Если это понадобится как факт — нужен `fetch --unshallow` или
  прикрепление репозитория.
- Их envelope не несёт ссылок на доказательства. Прежде чем переносить пункт 2,
  надо решить, кто в 007 отвечает за то, что `evidence refs` указывают на
  существующие файлы run record, — стадия или редьюсер.

## Вердикт

Изучить внимательно, забрать протоколы и policy-паттерны, не тащить Bash-государство.

По дисциплине вокруг ошибок, тестовых вердиктов и бюджетов репозиторий заметно
взрослее большинства аналогов. Самая ценная его идея — `unmeasured` — у 007 уже
есть в виде правила (`ERROR`), но без механизма. Механизм и стоит взять.
