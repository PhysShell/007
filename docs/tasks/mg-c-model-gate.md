# Задача MG-C: `o7-model-gate` — заморозка контракта (contract-first, docs-only)

> Идентификаторы этапов: **SB-A0** (`sandboy-a0-contract-red.md`) → **SB-A1**
> (`sandboy-a1-vertical-b.md`) → **SB-A2** (retirement Own.NET) → **SB-B**
> (`docs/architecture/capability-fd-transport.md`) → **MG-C** (этот документ).
> Префикс SB- обязателен: голые «A0»/«A1» конфликтуют с Q-Deck A0/A1
> (`docs/q-deck/`).

Статус: **ACCEPTED / CLOSED / FROZEN** после корректирующих раундов R1–R5.3
(§16). Реализация отсутствует и в этом срезе запрещена.

```text

implementation       BLOCKED
                       1. ратификация credential-поправки мейнтейнером (§8)
                       2. состояние пререквизитов SB-A0/SB-A1/SB-B (§2)
execution priority   без изменений — A1-V0 (TODO.md, `bc700b1…`)
следующий            SB-A0 (`allow_read` + подъём policy digest)
пререквизит MG-C
```

Дальнейшие раунды не планируются. Документ пересматривается при двух событиях:
изменении зависимостей, закреплённых в §1 и §13 (в частности идентичности
гранта SB-B), либо при наступлении очереди MG-C по §12.

Реализация дополнительно заблокирована двумя независимыми условиями:
ратификацией credential-поправки мейнтейнером (§8.2) и состоянием пререквизитов
(§2). Ни одно из них не снимается этим документом.

Этот документ — нормативный контракт будущего этапа MG-C. Он не является
разрешением на реализацию. Ни одна строчка `o7-model-gate` не написана, и
пререквизиты MG-C на момент заморозки не выполнены (§2). Документ существует
ровно для того, чтобы будущая реализация не выбирала архитектуру кодом.

Порядок чтения: §2 (что реально есть в дереве) → §3 (граница доверия) → §4

## 3. Граница доверия MG-C (заморожено)

```text
trusted controller / launcher
        |
        | (SB-B) pre-opened, policy-bound capability — вне scope MG-C
        v
sandboxed target
        |
        | унаследованный дескриптор `model_invoke`, и ничего больше
        v
  o7-model-gate                (доверенный процесс вне песочницы)
        |
        | credential вводится внутри доверенной стороны
        v
      ArliAI
```

**Доверенная сторона никогда не передаёт** sandboxed target'у:

- ArliAI API key или любой другой upstream-credential;
- bearer-токен, воспроизводимый где-либо ещё;
- произвольный upstream URL;
- произвольные `Authorization`/иные заголовки;
- generic provider-конфигурацию (base_url, provider, endpoint);
- authority создать замену соединения с брокером;
- generic сетевую authority ради доступа к ArliAI.

Формулировка намеренно про **то, что передаёт доверенная сторона**, а не про
«в песочницу не может попасть credential никаким путём» (уточнено R5.2).
Второе — заявление и о содержимом ответа провайдера, а его граница задана
моделью угроз **§8.6** и там же единственный раз определена: 2xx model output
является declassification-каналом, блокируется только дословное вхождение.
Категорическая версия противоречила бы §5.5/§8.6, а не усиливала их.

Примитив MG-C — **action capability**, а не HTTP-прокси, прячущий секрет.
Обходной путь «URL + bearer-токен внутрь песочницы» не является частичной
реализацией MG-C и не принимается ни как временный, ни как демонстрационный.
Он уничтожает ровно то свойство, ради которого этап существует, и противоречит
Non-goals SB-B («No bearer tokens or secrets over this transport, ever»,
`51f97d9…`).

## 4. Граница слоёв SB-B ↔ MG-C (заморожено)

```text
SB-B владеет:   доставкой authority
MG-C владеет:   интерпретацией authority и вызовом модели
```

MG-C **не переопределяет и не реализует** ничего из перечисленного — это
deliverables SB-B (`51f97d9…`):

- capability-манифест и его канонический digest;
- маппинг `target_fd`, staging/scrub/dup3-дисциплину;
- хореографию SCM_RIGHTS (два хопа) и single-owner invariant;
- authorization barriers 1 и 2 и их state machine;
- `CapabilityEvidence`, survivor-set proofs, post-exec `fd_probe`;
- protocol v2, его frame grammar и правило запрета downgrade;
- семантику владения дескриптором в monitor/child.

MG-C **начинается там**, где уже существует авторизованное, открытое соединение:
у gate есть подключённый дескриптор, у target'а — унаследованный `target_fd`.
Всё, что до этого, MG-C принимает как данность и на что опирается — фиксируется
в §9 как зависимость, а не как собственная работа.

Один нюанс, который MG-C обязан учесть, но не решает: пример манифеста SB-B
объявляет capability как `{ "name": "model_invoke", "target_fd": 3,
"kind": "unix_stream" }`. Границ сообщений `unix_stream` не сохраняет, поэтому
**MG-C определяет собственное обрамление поверх потока** (§5.2). Если SB-B при
реализации предложит для этой capability seqpacket-`kind`, длина-префикс MG-C
остаётся внутренней границей размера — ровно так, как SB-B формулирует это для
собственного v2.

## 5. RPC-контракт MG-C v1 (заморожено)

### 5.1 Версия и запрет переговоров

- Поле `protocol_version` присутствует в каждом кадре; в v1 обязано быть равно `1`.
- Неизвестная версия → **fail closed**: один терминальный кадр отказа, затем
  закрытие соединения. Ни negotiation, ни downgrade, ни «прочитать и
  проигнорировать» не существует (зеркало правила SB-B о запрете downgrade).
- Расширение грамматики — это версия v2, а не молчаливое добавление полей.

### 5.2 Обрамление

Повторяет конвенцию кадра репозитория (`9ff25d6…`), а не изобретает новую:

```text
frame = length (u32 BE, длина тела) || body
```

- Тела кадров `bind`, `bound`, `invoke`, `response`-заголовка и `rejected` —
  JSON с `deny_unknown_fields` и обязательным полем `type`. Неизвестный `type`
  → fail closed, без «прочитать и пропустить».
- Кадр тела ответа — **непрозрачные байты**, не JSON (см. §5.5).
- Заявленная длина, не совпадающая с фактически прочитанным, обрыв в середине
  кадра, мусор после терминального кадра → fail closed.
- Превышение объявленной границы размера проверяется **до аллокации**, по
  префиксу длины.

### 5.3 Границы (явные, а не унаследованные из библиотек)

| константа | значение | обоснование |
|---|---|---|
| `MG_MAX_REQUEST_BYTES` | 1 MiB | совпадает с `MAX_REQUEST_BYTES` (`8194d02…`); prompt + JSON Schema должны в него укладываться, иначе запрос отвергается до аллокации |
| `MG_MAX_RESPONSE_HEADER_BYTES` | 64 KiB | совпадает с `MAX_REPORT_BYTES` (`9ff25d6…`) |
| `MG_MAX_RESPONSE_BODY_BYTES` | 10 MiB | равно `MAX_ARLIAI_RESPONSE_BYTES` (`752dd76…`, `e42dc1d…`) — граница не изобретается, а наследуется от уже принятого контракта |
| `MG_MAX_CONNECTIONS` | явное малое число, фиксируется реализующим срезом | верхняя граница одновременно обслуживаемых соединений; безлимитный accept запрещён |
| `MG_MAX_INVOCATIONS_PER_CONNECTION` | **1** | capability single-shot, §5.4 |

### 5.4 Время жизни capability: single-shot, очереди нет

**Заморожено (R1): одна capability = одно соединение = ровно один вызов
модели.**

```text
bind (доверенная сторона, до передачи дескриптора)
  → invoke (песочница, ровно один)
  → response
  → close
```

- Любой второй кадр `invoke` в том же соединении — нарушение протокола: fail
  closed, соединение закрывается. Не важно, пришёл он до ответа или после.
- Внутренней FIFO-очереди, backpressure-семантики и «насыщения очереди» в M1
  **не существует**, потому что их нечем оправдать: единственный
  предполагаемый первый потребитель (`o7 invoke`, `a84a4ee…`) делает ровно один
  запрос без retry (`752dd76…`, «No retry in this slice»).
- Ограничение ресурсов на уровне процесса — это `MG_MAX_CONNECTIONS`, а не
  очередь заданий.

**Почему single-shot, а не «произвольное число последовательных вызовов»
(правка R1).** Первая редакция разрешала соединению обслуживать неограниченное
число вызовов подряд. Это бесплатно выдавало неограниченную
модельную/вычислительную authority из одного грант-акта, причём ни один
существующий потребитель этого не просил: `o7 invoke` делает один POST без
retry, а корректирующий цикл A1-V0 — это отдельный запуск на раунд, то есть
отдельный launch и отдельный манифест SB-B. Манифест SB-B привязан к запуску
(`51f97d9…`, Decision 1), поэтому «одна capability на запуск = один вызов на
запуск» — согласованная, а не произвольная граница. Расширение (N вызовов,
connection-bound budget) — это версия протокола, а не свободное свойство v1.

### 5.5 Грамматика: две фазы, разные стороны доверия

Соединение живёт в двух фазах, и **разные стороны говорят в разных фазах**.

**Фаза 1 — bind. Говорит только доверенный launcher, до передачи дескриптора
в песочницу.** Ровно один кадр:

```json
{
  "protocol_version": 1,
  "type": "bind",
  "invocation_profile": "<имя профиля>",
  "cap_grant_nonce": "<32 lowercase hex, минченный родителем для ЭТОГО гранта>"
}
```

Ответ — ровно один кадр `{"protocol_version": 1, "type": "bound",
"invocation_profile": "<эхо>", "model": "<разрешённая идентичность модели>",
"cap_grant_nonce": "<эхо>"}` либо `rejected` (§5.6).

Перед ответом `bound` gate выполняет **преflight условий, известных ему заранее**
(правка R2): TRACE-состояние `log`-фасада (§8) и читаемость доверенного
источника credential. Оба отказывают в фазе 1, до того как capability вообще
будет выдана. Проверка читаемости источника **не удерживает значение** — она
устанавливает доступность, а не читает секрет в буфер, живущий дольше проверки.
Обе проверки повторяются в фазе 2 (`log::max_level` изменяем в рантайме, файл
может исчезнуть между фазами), то есть преflight — это ранний отказ, а не замена
fail-closed проверке в момент вызова.

После успешного `bound` профиль **связан с этим соединением навсегда**. Любой
последующий кадр `bind` — нарушение протокола (`already_bound`), соединение
закрывается. Дескриптор передаётся в песочницу только после `bound`; песочница
физически не участвует в фазе 1 и не может её повторить.

**`cap_grant_nonce` — корреляционная идентичность, а не аутентификатор (R2).**
Родитель уже минтит его для каждого гранта, несёт в кадре CAP_GRANT и получает
эхо в `CapabilityEvidence` (`51f97d9…`, Decisions 3 и 5). MG-C **не изменяет
грамматику манифеста SB-B и не добавляет Sandboy знаний о моделях** — он лишь
использует уже существующую идентичность на доверенной стороне, чтобы
gate-запись можно было сопоставить с `CapabilityEvidence` того же гранта (§14).

Чего этот nonce **не** делает: он не аутентифицирует того, кто прислал `bind`.
Значение известно родителю, монитору и — после CAP_GRANT — самому child'у.
Доверие фазы 1 держится на двух других вещах: на **моменте** (bind происходит до
того, как дескриптор покидает доверенную сторону) и на недостижимости точки
приёма из песочницы (§5.8). Реализация, которая начнёт трактовать nonce как
секрет или как право, воспроизведёт ровно тот дефект, который R1 закрывал.

**Фаза 2 — invoke. Говорит песочница.** Ровно один кадр (§5.4):

```json
{
  "protocol_version": 1,
  "type": "invoke",
  "request_id": "<32 lowercase hex>",
  "prompt": "<UTF-8 текст>",
  "schema": { }
}
```

Ответ на принятый `invoke` — заголовок, за которым следует кадр тела **тогда и
только тогда, когда `body_bytes != null`**.

```json
{
  "protocol_version": 1,
  "type": "response",
  "request_id": "<эхо запроса>",
  "outcome": "http | timeout | transport | redirect | too_large
              | credential_reflected",
  "http_status": 200,
  "invocation_profile": "<связанный с соединением, эхо>",
  "model": "<разрешённая профилем идентичность модели>",
  "error_kind": "<из закрытого множества, если outcome != http>",
  "detail": "<опционально, из закрытого множества формулировок>",
  "body_bytes": 1234
}
```

**Правило обрамления ответа (уточнено R4.1):**

```text
body_bytes = N (включая 0)  → следует РОВНО ОДИН кадр тела длиной N;
                              N = 0 — это настоящее пустое тело провайдера
body_bytes = null           → кадра тела НЕ следует вовсе
```

Тело, когда оно следует, — **сырое тело HTTP-ответа провайдера, байт в байт**.

`body_bytes = null` возникает у исходов, где полного тела для пересылки не
существует **или** оно существует, но не является sandbox-facing данными:

```text
timeout | transport | redirect | too_large   тела не существует
http, статус не 2xx                          тело существует, но это
                                             diagnostic channel провайдера —
                                             НИКОГДА не пересекает границу
                                             песочницы (§5.5, R5)
credential_reflected                         2xx-тело содержит дословный
                                             credential — не пересылается;
                                             error_kind = "credential_reflected"
```

Различать «тела не было» и «тело есть, но не пересылается» на wire не нужно:
для песочницы оба означают одно — данных нет. Различение сохраняется на
доверенной стороне, где audit несёт `response_bytes` и `response_body_digest`
физически полученного тела (§14).

Различие `body_bytes = 0` и `body_bytes = null` — то же различие, что между
`Some(digest(b""))` и `null` в §14: «провайдер вернул пустое тело» и «тела для
пересылки нет» — разные утверждения, и одно значение на оба было бы ложным
свидетельством на wire.

**Полная схема заголовка по исходам (правка R4.2).** Пример выше показывает
форму, но не отвечает, что происходит с `http_status`, когда статуса не
существует, и какое именно значение принимает `error_kind`. Без этого
производитель и строгий клиент могут разойтись, оба считая себя
соответствующими контракту:

| `outcome` | `http_status` | `error_kind` | `body_bytes` |
|---|---|---|---|
| `http`, статус **2xx** | код ответа (u16) | **отсутствует** | `N` (включая 0) |
| `http`, статус **не 2xx** | код ответа (u16) | **отсутствует** | `null` — тело не пересылается (§5.5, R5) |
| `timeout` | `null` | `"timeout"` | `null` |
| `transport` | `null` | `"transport"` | `null` |
| `redirect` | `null` | `"redirect"` | `null` |
| `too_large` | `null` | `"response_too_large"` | `null` |
| `credential_reflected` | код ответа (u16), всегда 2xx | `"credential_reflected"` | `null` |

Правила, из которых таблица выведена:

- `http_status` — **всегда присутствует как ключ**, значение `null`, когда
  HTTP-ответа не было. Не «опускается»: отсутствующий ключ и `null` — два
  разных состояния для строгого парсера, и выбор между ними не должен
  оставаться на усмотрение реализации;
- `error_kind` присутствует **тогда и только тогда**, когда `outcome != http`;
- значения `error_kind` намеренно совпадают со словарём уже принятой
  классификационной матрицы (`752dd76…`): `timeout`, `transport`, `redirect`,
  `response_too_large`. Второго словаря для тех же условий не заводится;
- `credential_reflected` сохраняет `http_status`: провайдер ответил, статус
  известен и является честной уликой; не переслано только тело.

Отказ — **ровно один кадр, без кадра тела** (§5.6):

```json
{
  "protocol_version": 1,
  "type": "rejected",
  "request_id": "<эхо, либо null>",
  "error_kind": "<из закрытого множества>",
  "detail": "<опционально, из закрытого множества формулировок>"
}
```

Чего в кадре `invoke` нет и быть не может (проверяется `deny_unknown_fields` +
отсутствием соответствующих полей в грамматике): `invocation_profile`,
`base_url`, `endpoint`, `api_key`, `authorization`, `headers`, `proxy`,
`provider`, `model`, `timeout`, `stream`, `max_redirects`. Попытка передать
любое из них — malformed request, а не частично принятый запрос.

**Почему `invocation_profile` исчез из кадра песочницы (правка R1, P0).**
Первая редакция позволяла sandboxed caller'у назвать профиль, а gate лишь
проверял, существует ли такое имя в доверенной конфигурации. Это не scoping
authority, а её отмывание: при профилях `reviewer-cheap`, `reviewer-strong`,
`long-context` обладатель одной generic `model_invoke` capability получал бы
authority на все известные gate профили сразу. Записанный тогда инвариант
«профиль никогда не расширяет capability-профиль вызова» был **декларацией без
механизма** — authority declaration и authority decision находились в разных
местах. Двухфазная привязка и есть механизм: решение принимает та же доверенная
сторона, которая владеет грантом, до того как второй конец попадает в песочницу.
Идентичность модели тем самым тоже становится свойством capability-соединения,
а не выбором недоверенного вызывающего.

**Почему возвращается сырое тело, а не извлечённый контент.** Три причины,
каждая — из уже принятого контракта (`752dd76…`): (1) `stdout.raw` нормативно
определён как «raw HTTP response body, byte-for-byte» и остаётся уликой
провайдера; (2) вся классификационная матрица (`empty_choices`, `null_content`,
`tool_calls_present`, `invalid_json`, `schema_violation`, …) уже живёт в
`classify_arli` (`a84a4ee…`), и повторная её реализация в gate создала бы
второй, расходящийся ArliAI-контракт — прямо запрещено §7 постановки задачи;
(3) чем меньше gate интерпретирует, тем меньше доверенного кода. Gate отвечает
за **транспорт и credential**, а не за смысл ответа. Локальная re-валидация по
JSON Schema остаётся единственным судьёй, как и сегодня.

**Механика разделения каналов по HTTP-семантике (правка R5, P0).**

> Этот раздел описывает **что делает gate**. Граница гарантии — какое именно
> обещание из этого следует и где оно кончается — определена в **§8.6** и здесь
> не пересказывается (правило единственного места, R5.2). При расхождении между
> текстом ниже и §8.6 старшинство у §8.6.

Провайдер — доверенный получатель credential и одновременно недоверенный
источник диагностик. Отсюда разделение каналов:

```text
non-2xx  diagnostic channel
         тело НИКОГДА не пересекает границу песочницы
         классификация выводится вызывающим ИЗ СТАТУСА (752dd76…):
         401/403 → auth, 402/429 → usage, 408 → timeout,
         прочие 4xx → http_request_rejected, 5xx → http_5xx —
         extract_content до этих случаев не доходит вовсе

2xx      successful model-output channel
         сырое тело пересылается: именно по нему работает существующий
         классификатор (envelope, choices, tool_calls, content, JSON)
         и локальная schema-валидация
```

Diagnostic-тело песочнице функционально не нужно **ни для результата, ни для
классификации** — пересылать его значило отдавать недоверенной стороне байты
ради удобства диагностики, расширяя множество мест, куда может попасть
отражённый credential. Именно там отражение и происходит: на `752dd76…`
зафиксирован живой `400`, тело которого эхом возвращает путь поля запроса.

**Containment-проверка на 2xx-пути.** Перед отправкой тела gate обязан
убедиться, что оно не содержит **точных байт** credential, использованного в
заголовке `Authorization`. При совпадении тело не пересылается: исход
`credential_reflected` (§5.6), событие в audit (§14). На non-2xx проверка для
решения о пересылке не нужна — тело запрещено безусловно, и превращать честный
`401` в `credential_reflected` значило бы потерять основную классификацию.

Чем эта проверка **является** с точки зрения обещания — defense in depth поверх
границы §8.6, а не самостоятельная гарантия, — сказано в §8.6. Здесь она
описана как обязанность реализации, и не более.

Почему это не нарушает принцип: проверка — **байтовое вхождение известной
подстроки**, а не разбор ответа. Она не знает ни про `choices`, ни про
`content`, ни про `finish_reason`, не порождает второго классификатора и не
меняет того, что `classify_arli` остаётся единственным судьёй смысла. Она
отвечает на один вопрос — «не вынесет ли этот байтовый поток секрет за границу
доверия», — то есть относится к credential-плоскости, за которую gate и так
отвечает.

Почему она обязательна: gate отправляет ключ вверх по течению и, без этой
проверки, пересылает вниз всё, что вернул провайдер. Тогда §8.5 («credential
не становится видимым песочнице через тело ответа») была бы утверждением,
которое ни одна реализация не способна выполнить: достаточно, чтобы провайдер
отразил заголовок в диагностике. Основание не гипотетическое — на закреплённом
`752dd76…` зафиксировано живое наблюдение, что этот endpoint отражает
содержимое запроса в теле ошибки (`400` с `loc: ('body','response_format',…,
'json_schema','name')`). Заголовки — не тело запроса, но «этот endpoint
возвращает фрагменты запроса в диагностике» здесь установленный факт, а не
предположение.

Граница гарантии названа точно: проверка ловит **дословное** вхождение. Она не
поймает преобразованное отражение (base64, усечение, смена регистра,
экранирование). Остаточный риск зафиксирован в §8.5 как остаточный, а не
закрыт формулировкой.

### 5.6 Таксономия ошибок

Два непересекающихся класса.

**A. Исходы провайдера** — обязаны отображаться 1:1 на существующие
`ArliOutcome` (`e42dc1d…`), чтобы `classify_arli` оставался единственным
классификатором:

| `outcome` | соответствие `ArliOutcome` |
|---|---|
| `http` (+ `http_status`) | `Http { status, body }` |
| `timeout` | `TimedOut` |
| `redirect` | `Redirect` |
| `too_large` | `TooLarge` |
| `transport` | `Transport` |
| `credential_reflected` | `Http { body }` со статусом **2xx**, **не переслан**: тело содержало точные байты credential (§5.5, R4/R5) |

`credential_reflected` принадлежит классу A, а не B, именно потому, что
провайдер **был вызван**: инвариант класса B («ни один `rejected` не
сопровождается обращением к провайдеру») остаётся неповреждённым. Кодируется он
кадром `type: "response"` с `body_bytes: null` и
`error_kind: "credential_reflected"` (§5.5) — не кадром `rejected`, который
утверждал бы, что обращения к провайдеру не было.

**B. Отказы gate до обращения к провайдеру** — кадр `type: "rejected"` с
`error_kind` из закрытого множества.

**Значение `request_id` определяется ОДНИМ структурным правилом, а не
принадлежностью к группе (правка R4):**

```text
request_id != null  ⟺  валидный конверт `invoke` был разобран
```

Это правило единственное и не имеет исключений. Группы ниже классифицируют
kind'ы по тому, **где они могут возникнуть**, и не переопределяют правило ID:
kind, возможный в обеих фазах, в фазе 1 несёт `null`, в фазе 2 — эхо.

```text
B1 — возможны ТОЛЬКО до разбора конверта (request_id всегда null,
     отказ терминален для соединения)

unknown_version         версия протокола не 1
malformed_frame         длина не совпала с прочитанным / не JSON /
                        неизвестное поле / неверный тип / отсутствует request_id
request_too_large       превышен MG_MAX_REQUEST_BYTES (по префиксу длины,
                        до аллокации и до разбора JSON)
bind_required           первый кадр соединения не bind, либо invoke до bound
already_bound           второй кадр bind в том же соединении
unknown_profile         профиль отсутствует в доверенной конфигурации
malformed_nonce         cap_grant_nonce не 32 lowercase hex

     unknown_profile и malformed_nonce достижимы только доверенной
     стороной — песочница фазы 1 не касается.

B2 — возможны ТОЛЬКО после разбора конверта `invoke` (request_id всегда эхо)

second_invocation       второй кадр invoke в соединении — НЕОБЯЗАТЕЛЬНЫЙ ответ,
                        см. ниже

B3 — возможны в ЛЮБОЙ фазе; request_id по структурному правилу выше

credential_unavailable  доверенный источник credential недоступен/пуст
trace_logging_refused   глобальный log max level допускает TRACE (§8)
shutting_down           gate завершается и новых вызовов не принимает
```

**Почему введена группа B3 (правка R4).** R2 добавил преflight этих трёх
условий в фазу `bind`, но оставил их kind'ы перечисленными под заголовком B2,
чей определяющий признак — «`request_id` известен и ОБЯЗАН быть возвращён
эхом». Клиент, реализующий таксономию буквально по спискам, потребовал бы
non-null `request_id` для `credential_unavailable`, а законный отказ фазы 1
обязан нести `null` — то есть корректная реализация gate нарушала бы
замороженный контракт, и доверенный launcher мог бы отвергнуть собственный
ранний отказ. Оговорка в прозе противоречила структурному размещению; R4 убирает
причину, а не следствие: признак группы — фаза возникновения, признак ID —
единственное правило выше.

**`second_invocation` — разрешённый, но не обязательный ответ (правка R2).** При
истинном single-shot gate закрывает соединение сразу после ответа, поэтому
второй `invoke` физически может получить EOF/EPIPE и никогда не быть прочитанным.
Требовать в этом случае «красивый кадр отказа» означало бы навязать gate'у
удержание соединения ради диагностики. Нормативное acceptance-свойство здесь —
**«второй вызов провайдера невозможен»**, а не «получен кадр `rejected`»; §9.2
проверяет именно отсутствие второго upstream-вызова.

**Почему разделение (правка R1).** Первая редакция требовала в каждом ответе
`request_id: "<эхо запроса>"`, но одновременно требовала обнаруживать
`request_too_large` по префиксу длины — то есть **до** того, как какой-либо
`request_id` вообще прочитан. Контракт требовал сериализовать значение, которого
не существует. Теперь `request_id` типизирован как `string | null`, и nullable
он ровно в тех случаях, когда корреляции физически нет.

Дисциплина отправки на пути B1: gate отправляет **ровно один** кадр `rejected` и
закрывает соединение. Обрамление в этот момент уже могло рассинхронизироваться,
поэтому клиент обязан трактовать любую неудачу разбора этого последнего кадра
как то же самое терминальное состояние — не как повод продолжать.

Инвариант класса B: **ни один `rejected` не сопровождается обращением к
провайдеру** и никогда не несёт кадра тела. Это отличает «ничего не
выполнялось» от «провайдер ответил» и поддерживает границу FAIL/BLOCKED,
зафиксированную в `752dd76…`.

**Отложенное решение (§13):** отображение класса B в `InvokeStatus` на стороне
вызывающего. Ни одно существующее значение не означает «доверенный gate отказал
до вызова провайдера»; `BlockedProvider` был бы ложью (провайдера не было),
`BlockedNotInstalled` — натяжкой. Введение нового `BLOCKED_*` — изменение
словаря, которое, согласно `a84a4ee…` и `752dd76…`, связано с кросс-репозиторной
конформностью Demand Radar. Решение принимается реализующим MG-C срезом с той же
дисциплиной, что прошёл `BLOCKED_PROVIDER`, и **не принимается здесь**.

### 5.7 Отмена: bounded-by-timeout, а не гарантированное прерывание

- Отдельного кадра `cancel` в v1 **нет**. При правиле single-shot закрытие
  дескриптора — полный и однозначный примитив отмены; второй канал сообщений
  противоречил бы §5.4.
- Отмена = клиент закрывает свою сторону. Gate обязан наблюдать EOF/EPIPE,
  **отбросить результат**, не выполнять retry и не начинать нового запроса,
  записать audit-запись с терминальным классом `client_disconnected`.
- **Заморожена слабая (bounded) форма (правка R1):** незавершённый
  upstream-вызов может дожить до upstream-таймаута профиля, и это допустимо.
  Верхняя граница ущерба — один запрос (§5.4, single-shot) в пределах
  доверенного таймаута.
- Ответ не отправляется частично: если клиент исчез до отправки заголовка,
  ответ не отправляется вовсе; частично отправленный ответ — терминальное
  состояние соединения, не повод к повторной попытке.
- Upstream-таймаут задаётся **профилем на доверенной стороне**. Клиентские
  таймауты в грамматике отсутствуют.
- Соединение обслуживает ровно один вызов и закрывается (§5.4).

**Почему форма ослаблена (правка R1).** Первая редакция требовала «прервать
незавершённый upstream-вызов». Существующий слой ArliAI этого не предоставляет:
`invoke_arliai::call` (`e42dc1d…`) синхронен, возвращает управление только по
завершении транзакции `ureq` и не отдаёт наружу никакого cancellation handle.
Требование было не бесплатным свойством существующего кода, а **новым
существенным транспортным требованием**, записанным как данность. Сильная форма
(доказуемая прерываемость upstream-вызова) остаётся возможной целью, но она
обязана прийти вместе с доказательством прерываемости, а не вместе с
формулировкой в контракте.

Зависимость, которую MG-C **не обеспечивает сам**: надёжность EOF как сигнала
смерти target'а обеспечивается single-owner invariant SB-B (`51f97d9…`,
Decision 2) — «target exit ⇒ broker-observable EOF». Если у родителя или
монитора останется живая копия дескриптора, gate EOF не увидит. Это записано в
§9 как зависимость MG-C от SB-B.

### 5.8 Приём соединений и порядок передачи дескриптора

Полный порядок, в котором authority связывается раньше, чем попадает в
песочницу (правка R1):

```text
0. SB-B barrier 1 пройден (sandbox report проверен родителем)
1. родитель минтит cap_grant_nonce для ЭТОГО гранта      [уже требование SB-B]
2. доверенный launcher соединяется с точкой приёма gate
3. launcher отправляет bind(invocation_profile, cap_grant_nonce)  [фаза 1, §5.5]
4. gate связывает профиль с ЭТИМ соединением, отвечает bound
5. только теперь launcher передаёт свой конец через CAP_GRANT — тот же
   дескриптор, тот же cap_grant_nonce                    [SB-B, barrier 2]
6. песочница отправляет invoke — без права назвать профиль
7. gate обслуживает ровно один вызов и закрывает соединение
```

Шаг 5 строго после шага 4: если дескриптор ушёл в песочницу до `bound`,
authority выбирается уже недоверенной стороной, и вся конструкция теряет смысл.
Порядок — обязанность launcher'а; gate обеспечивает свою половину тем, что
`invoke` до `bound` отвергается (`bind_required`), а повторный `bind` —
отвергается всегда (`already_bound`).

Шаг 1 существует в SB-B независимо от MG-C (`51f97d9…`, Decision 3: nonce
минтится родителем после barrier 1 и эхоится в `CapabilityEvidence`). R2 лишь
требует, чтобы **тот же** nonce попал в кадр `bind`, — это единственное новое
требование к launcher'у сверх порядка операций.

- Gate **никогда не инициирует** соединение к клиенту и не принимает от клиента
  адрес назначения.
- Gate имеет одну точку приёма, принадлежащую доверенной стороне. Её путь
  **не должен появляться ни в одном policy root'е target-песочницы** — это уже
  сформулировано в adversarial-матрице SB-B (`51f97d9…`, последний пункт) и
  здесь не переопределяется, а наследуется.
- **Честная формулировка свойства:** «дочерний процесс не может переподключиться»
  — это свойство SB-B (Landlock-запрет пути) плюс прав файловой системы в
  развёртывании, **а не** свойство, которое gate способен обеспечить сам. MG-C
  не имеет права утверждать его как собственное.

## 6. Семантика логического профиля (заморожено)

- **Профиль привязан к соединению, а не выбирается вызывающим** (§5.5, §5.8).
  Выбор делает доверенный launcher в фазе `bind`, до передачи дескриптора;
  песочница профиль не называет и сменить не может.
- Имя профиля: charset и границы — те же, что у имени capability в SB-B
  (`[a-z0-9_.-]`, ≤ 64 байт). Одна конвенция вместо второй.
- Профиль содержит **только то, что действительно варьируется** (правка R1):

  ```text
  model                  идентичность модели
  upstream_timeout       доверенный таймаут вызова
  ```

- Поля `credential_source_id` в профиле **нет** (правка R2). В M1 доверенный
  источник credential ровно один (§8.4), значит варьировать нечего, а поле
  было бы абстракцией под воображаемый второй backend — ровно тот жанр, который
  §11 запрещает. Заменяемость источника (шов под Agent Vault) — свойство gate,
  а не измерение профиля.

- Профиль **НЕ содержит** `provider` и `endpoint`: и то и другое заморожено на
  этапе компиляции (§7). Профиль, способный назвать endpoint, снова расширил бы
  поверхность перенаправления credential — пусть и требуя для этого доступа к
  доверенной конфигурации, но это уже другое security property, чем «no flag,
  env var, or config may repoint the Authorization-carrying call» (`752dd76…`).
  Multi-provider — non-goal (§11), так что варьировать нечего.
- Профили задаются доверенной конфигурацией. В протоколе профиль — **только имя,
  и только в кадре `bind`**.
- Неизвестный профиль → отказ, fail closed, в фазе `bind`. **Профиля по
  умолчанию не существует**, fallback запрещён. Это прямое повторение уже
  реализованного поведения `--capability-profile` (`a84a4ee…`, строки 233–239:
  неизвестное значение отвергается «rather than silently narrow or widen it»).
- Идентичность модели приходит из профиля, не из RPC. Это сохраняет уже принятое
  требование `752dd76…` — отказ от provider-selected default model, потому что
  «a call whose model the provider silently chose is not attributable evidence».
  Заголовок ответа возвращает разрешённую модель, чтобы вызывающий по-прежнему
  всегда записывал непустой `model` в `meta.json`.

**Решение по столкновению имён.** В дереве уже есть `--capability-profile` с
единственным значением `read-only-data` (`a84a4ee…`), и он описывает **другую
ось**: под какой authority выполняется вызов. Поле MG-C называется
`invocation_profile` и описывает **доверенную привязку провайдера**. Два разных
понятия не получают одно имя.

Инвариант «профиль MG-C не может выдать вызывающему authority, которой у него не
было» держится **не декларацией, а механизмом**: вызывающий не участвует в
выборе профиля вообще (§5.5, фаза 1). Первая редакция записывала этот инвариант
как утверждение при том, что RPC позволял песочнице назвать любой известный
профиль; правка R1 убрала расхождение между заявлением и механизмом.

*Замечание о достоверности ссылки (`AGENTS.md`, «Grounding factual claims»):*
комментарий в `src/invoke.rs` атрибутирует формулировку «a capability-profile
claim that isn't actually enforceable must refuse, not silently downgrade»
документу `docs/security-layers.md`; на закреплённом blob'е такой фразы там нет.
Поэтому выше цитируется **само поведение кода** (проверяемый факт), а не
пересказ. Расхождение зафиксировано как наблюдение, его исправление — не задача
MG-C.

| `tool_choice: "none"` | наследуется |
| `stream: false` | наследуется (см. §11 — стриминг non-goal) |
| reasoning-контролы не отправляются | наследуется |

| разделение FAIL (2xx с непригодным payload) / BLOCKED (не-2xx) | наследуется; класс B §5.6 не смешивается ни с тем, ни с другим |
| независимая локальная валидация по JSON Schema как единственный судья | наследуется; gate не валидирует за вызывающего |
| **`stdout.raw` = тело только для 2xx; non-2xx diagnostic body не является canonical evidence** | наследуется из поправки к `docs/o7-invoke.md` (R5). MG-C **не заводит** второй, расходящейся evidence-семантики для gate-brokered вызовов — правило исправлено уровнем выше и наследуется как есть |

MG-C **добавляет** ровно два отличия, оба заявлены явно:

1. **Кто держит credential** — новый доверенный процесс вместо процесса `o7`.
   Это изменение границы, требующее ратификации (§8).
2. **Кто выбирает модель** — профиль, связанный с capability-соединением, вместо
   `--model` вызывающего. Это ужесточение (вызывающий теряет authority), а не
   ослабление; требование атрибутируемости модели сохраняется, а разрешённая
   идентичность возвращается в `bound` и в заголовке ответа.

Второго, противоречащего ArliAI-контракта не создаётся: при конфликте
формулировок **старшинство у `docs/o7-invoke.md`**, а расхождение подлежит явной
правке того документа, а не молчаливому расхождению.

## 8. Граница credential и поправка, ТРЕБУЮЩАЯ РАТИФИКАЦИИ МЕЙНТЕЙНЕРОМ

### 8.1 Что заморожено сегодня

`AGENTS.md` (`07cb3a7…`, правило 1) фиксирует **maintainer-ratified
credential-policy exception**, ограниченное `o7 invoke --engine arliai`, со
свойствами:

```text
ключ читается в момент вызова в один function-local owned value
в HTTP-слой уходит только borrowed trimmed view
никогда не хранится ни в одной структуре
никогда не попадает в artifact, run record, строку ошибки
вычищается из окружения каждого provider-субпроцесса
dispatch fail-closed отказывает, когда log max level допускает TRACE
```

Нормативный контракт — `docs/o7-invoke.md`, «Key handling». Там же: **любое
изменение, расширяющее места, куда может течь ключ, — находка P0.**

### 8.2 Конфликт, создаваемый MG-C

MG-C вводит **второй процесс, способный читать credential**. Это расширение
границы credential-authority по сравнению с закреплённым текстом. Следовательно:

> **MAINTAINER RATIFICATION REQUIRED.** Реализация MG-C не может начаться, пока
> поправка ниже не ратифицирована мейнтейнером. Агент вправе сформулировать
> поправку; принять её он не вправе. `AGENTS.md` этим документом не изменяется.

**Поправка не готова к ратификации, пока не закрыт upstream-контракт (R5).**
`docs/o7-invoke.md` получил корректирующую поправку «non-2xx body не является
canonical run evidence», но **реализация `run_arliai` ей ещё не соответствует**:
прямой путь `--engine arliai` по-прежнему пишет любое in-bound HTTP-тело в
`stdout.raw`. Пока это так, та самая diagnostic-body поверхность, которую MG-C
запрещает у gate, остаётся открытой в существующем прямом пути — и
ратифицировать расширение credential-границы, оставляя её, значило бы
ужесточить новое и не заметить старое. Порядок: сначала правка прямого пути,
затем ратификация §8.

### 8.3 Предлагаемая поправка (наиболее узкая из известных)

Расширить ратифицированное исключение с `o7 invoke --engine arliai` на
`{ o7 invoke --engine arliai, o7-model-gate }`, сохранив **форму жизненного
цикла ключа без ослабления**:

```text
запрос принят (после разрешения профиля)
→ доверенный источник credential читается в момент вызова
→ один function-local owned value
→ в HTTP-слой уходит только borrowed trimmed view
→ значение уничтожается по завершении вызова
```

Явно **отвергается** как ослабление:

```text
gate стартует → читает ARLIAI_API_KEY → держит его всё время жизни процесса
```

Резидентное владение секретом — именно то расширение мест утечки, которое
`AGENTS.md` называет P0; оно не принимается ни как оптимизация, ни как
«практичный компромисс».

Дополнительно поправка обязана сохранить:

- **TRACE-преflight** — вычисляется внутри процесса gate, до открытия соединения
  к провайдеру; при TRACE — `rejected/trace_logging_refused` (§5.6), никогда не
  тихая деградация;
- запрет попадания credential в `Debug`/сериализацию любой структуры gate;
- `detail`-строки в ответах — из закрытого множества формулировок, чтобы
  «в detail не попал ключ» было структурным свойством, а не обещанием ревью;
- в M1 gate не порождает субпроцессов; если когда-либо начнёт — правило
  `strip_provider_api_keys` (`a84a4ee…`) распространяется на него без исключений.

### 8.4 Источник credential: окружение процесса gate запрещено (правка R2, P0)

Первая редакция разрешала для разработки «переменную окружения доверенного
процесса». Для `o7 invoke` это корректно: процесс живёт примерно один вызов,
поэтому «резидентно всё время жизни процесса» и «резидентно на время вызова» —
одно и то же, и ратифицированное исключение покрывает случай целиком.

**Для долгоживущего gate это неверно.** При запуске вида

```text
ARLIAI_API_KEY=secret o7-model-gate
```

секрет находится в окружении и адресном пространстве процесса **всё время жизни
демона**, независимо от того, когда код вызовет `std::env::var`. Он читаем через
`/proc/<pid>/environ`, наследуется любым порождённым процессом и попадает в
core dump. Формулировка «читаем только во время вызова» описывает поведение
кода, а не резидентность значения, и не делает окружение менее резидентным.
Это ровно то расширение мест утечки, которое `AGENTS.md` квалифицирует как P0 —
то есть первая редакция запрещала резидентное владение в §8.3 и разрешала его
же через окружение в §8.4.

Заморожено:

```text
o7 invoke --engine arliai
    ARLIAI_API_KEY остаётся разрешён существующим исключением

o7-model-gate
    provider credential в окружении процесса ЗАПРЕЩЁН — в любом режиме,
    включая разработку и тесты
```

- Источник M1 — **доверенный credential-файл/дескриптор вне адресного
  пространства gate между вызовами**, читаемый call-scoped: открыть, прочитать
  в один function-local owned value, использовать borrowed trimmed view,
  уничтожить. Между вызовами gate не хранит ни значения, ни его копии.
- Правило делается **механическим, а не декларативным**: gate обязан отказаться
  стартовать, обнаружив provider-credential в собственном окружении, — тем же
  жанром fail-closed преflight'а, что и TRACE-проверка. Иначе «мы просто так не
  запускаем» остаётся обещанием развёртывания, а не свойством программы.
- Предпочтительный источник в развёртывании — файл, предоставленный systemd
  `LoadCredential`. **Реализация unit'а/модуля — вне этой задачи и вне M1**
  (§11); контракт фиксирует требование к источнику, а не его инсталляцию.
- Источник credential — заменяемый доверенный шов: будущий Agent Vault обязан
  подменять источник, **не изменяя ни одного байта sandbox-facing протокола**.
- В M1 источник ровно один, поэтому он не является измерением профиля (§6).

### 8.5 Инвариант невидимости

Инвариант разделён на две части, потому что у них **разная сила гарантии**
(правка R5.1). Смешивать их в один категорический список нельзя: часть каналов
порождает сам gate, а тело ответа порождает провайдер.

**(a) Каналы, которые gate порождает сам — закрыты структурно, без оговорок.**
Credential не становится видимым песочнице ни через: env, argv, унаследованный
дескриптор, кадр `invoke`, **все поля заголовка ответа** (`outcome`,
`error_kind`, `detail`, `model`, …), log, panic/error text, audit, окружение
субпроцесса. Gate просто не помещает туда credential; ни один из этих путей не
имеет исключений «для отладки».

**(b) Тело ответа — порождается провайдером, гарантия ограничена моделью угроз
§8.6.** Категорически заявлять «через ответ credential не пройдёт» здесь
нельзя: §5.5 объявляет 2xx model output явным declassification channel, и
блокируется только дословное вхождение. Ответ на 200 с `base64(credential)`
будет переслан. Это не дыра в реализации, а названная граница обещания —
см. §8.6.

**Тело ответа закрыто разделением каналов, а не фильтрацией (правка R5).**
Все пути выше закрыты структурно: gate просто не помещает туда credential.
Тело приходит от провайдера, поэтому здесь gate закрывает не источник, а
**выход** — и делает это по HTTP-семантике (§5.5):

```text
non-2xx diagnostic body   НИКОГДА не пересекает границу песочницы
2xx model output          пересылается; дословное вхождение байт
                          credential дополнительно блокируется
                          (credential_reflected, fail closed)
```

### 8.6 Threat model M1: что именно обещано (правка R5)

> **Правило единственного места (введено R5.2).** Граница модели угроз
> определена **здесь и только здесь**. Любое другое место документа, которое
> касается пути credential в песочницу, обязано **ссылаться** на §8.6, а не
> пересказывать границу своими словами. Три раунда подряд ловили один и тот же
> дефект: правило меняли в одном разделе, а его прежняя, более сильная
> формулировка оставалась жить в другом (§8.5 в R5.1, §3 и §9.3 в R5.2).
> Пересказ гарантии в N местах означает N мест, которые разойдутся при
> следующей правке.

> **M1 не заявляет confidentiality против злонамеренного или скомпрометированного
> upstream-провайдера.** Провайдер является **доверенным получателем** bearer
> credential. Gate предотвращает перенос credential по собственным каналам и не
> допускает provider diagnostic bodies через границу песочницы. Успешный
> 2xx model output является **явным declassification channel**; дословное
> отражение credential в нём дополнительно блокируется как defense in depth.

Почему граница именно здесь, а не строже. Требование «не пересылать
представление, способное нести credential» в буквальном виде невыполнимо:
получатель bearer-токена может вернуть произвольные байты, а закодировать ключ
можно как base64, hex, XOR, посимвольно, числами в JSON — список энкодеров не
имеет конца, и погоня за ним даёт видимость защиты, а не защиту. Перенос
`extract_content` внутрь gate тоже не помогает: злонамеренный провайдер положит
закодированный ключ прямо в `message.content`.

Поэтому остаточный риск после R5 имеет **другую форму**, чем после R4:

```text
было (R4):  машинерия валидации провайдера СЛУЧАЙНО отразила credential
            в диагностике, которую gate добросовестно переслал

стало (R5): доверенный получатель credential НАМЕРЕННО закодировал его
            в успешный model output
```

Первое — реалистичная авария, и она закрыта. Второе — компрометация провайдера
либо нарушение им собственного trust contract, то есть выход за пределы того,
что M1 обещает. Разница между «мы надеемся, что base64 не случится» и явной
моделью угроз в том, что вторая исполнима и проверяема.

Реализация обязана воспроизводить именно эти формулировки: заявлять
«credential не может попасть в песочницу через тело ответа» без разделения
каналов и без границы модели угроз — значит утверждать свойство сильнее
доказуемого, ровно та ошибка, которую §13 запрещает.

### 9.3 Финальная вертикаль MG-C

Достижима **только после SB-A1 GREEN и SB-B GREEN**:

```text
sandboxed process
  → унаследованная capability model_invoke
  → o7-model-gate
  → реальный вызов ArliAI
  → ответ
одновременно:
  прямой сетевой вызов из песочницы          → запрещён
  credential в env/argv/дескрипторах песочницы → отсутствует
  credential в полях, порождаемых gate         → отсутствует
  тело non-2xx-ответа доставлено в песочницу   → нет
  дословный credential в доставленном 2xx-теле → нет
```

**Условие приёмки сформулировано проверяемо, а не как «credential виден
внутри песочницы → нет» (уточнено R5.2).** Прежняя формулировка требовала
доказать отсутствие credential по **любому** пути, включая содержимое
успешного ответа провайдера, — то есть требовала опровергнуть то, что §5.5
и §8.6 явно разрешают. Реализация не смогла бы одновременно удовлетворить
условие приёмки и следовать разрешённому 2xx-relay. Перечисленные выше пять
пунктов проверяемы каждый по отдельности; всё, что за их пределами, ограничено
моделью угроз §8.6 и не является предметом приёмки M1.

Живой вызов ArliAI выполняется, когда credential/окружение доступны, и
**никогда не становится обязательным CI-гейтом** из-за того, что ключ оказался
на одной машине разработчика.

## 10. Шов для тестов gate до SB-B (разрешён с ограничением)

Разрешено: подать gate уже подключённый обычный `AF_UNIX` дескриптор (например,
из `socketpair`) и прогонять по нему свойства §9.2.

Запрещено формулировать результат таких тестов как доказательство того, что
capability-транспорт работает. Это тест **самого gate**, а не транспорта.
Формулировка в отчётах и коде обязана быть буквально такой.

Ограничения шва:

- шов не создаёт «второго способа доставки authority» — он лишь избавляет тест
  от необходимости иметь ядро с Landlock;
- шов не должен позволять production-пути gate принимать соединение, не
  пришедшее через доверенную точку приёма (§5.8);
- ни один тест этого шва не имеет права называться `capability_*` или иначе
  претендовать на словарь SB-B.

Конвенция исполнения (`358b387…`, `54085f9…`, `AGENTS.md`): тесты обязаны
компилироваться и быть зелёными в hosted-гейте; новые записи `--exclude` в CI —
находка P0. Тесты, требующие реального ядра, идут `#[ignore]` на выделенный
Linux-job, как это уже сделано в `616f301…`. RED-матрица MG-C, требующая типов
SB-B, **не пишется до SB-B**.

```text
  стабильную per-grant correlation identity,
  доступную доверенному launcher'у ДО CAP_GRANT,
  и присутствующую в CapabilityEvidence.

На blob'е 51f97d9 этой идентичностью является cap_grant_nonce
(Decisions 3 и 5).
```

```text
identity SB-B изменилась
  → закреплённая зависимость MG-C устарела
  → §5.5, §5.8, §9.2, §14 пересматриваются
```

архитектурным регрессом: транспорт снова начал бы знать, зачем используется

## 14. Контракт аудита (заморожено): только метаданные

Записывается на **доверенной стороне**, никогда не возвращается в песочницу:

```text
gate_invocation_id      идентификатор вызова, минтится доверенной стороной
request_id              эхо caller-минченного корреляционного id | NULL
invocation_profile      имя логического профиля
model                   разрешённая профилем идентичность модели
started_at / ended_at   отметки времени, плюс длительность
terminal_class          http | timeout | transport | redirect | too_large
                        | credential_reflected | rejected | client_disconnected
                        | bound_unused | bind_rejected
error_kind              из закрытого множества, когда применимо
http_status             когда terminal_class == http
request_bytes           размер принятого запроса
response_bytes          u64 | NULL — по тому же правилу, что digest (§ ниже)
cap_grant_nonce         идентичность гранта SB-B, связанная в фазе bind (§5.5)
prompt_digest           Digest256 — определение preimage ниже
response_body_digest    Digest256 | NULL — правило ниже
```

**Наличие полей определяется классом исхода, а не «обычно заполнено» (правка
R3.1).** Перечень выше — состав записи, а не обещание, что каждое поле всегда
имеет значение: у части исходов соответствующего события просто не было.
Заморожена **семантика наличия** (формат и место хранения по-прежнему
отложены — см. конец раздела):

| `terminal_class` | `profile` / `model` | `cap_grant_nonce` | `request_id`, `request_bytes`, `prompt_digest` | response-поля |
|---|---|---|---|---|
| `bind_rejected` | `model` — только если профиль успел разрешиться; иначе null | только если кадр `bind` разобран и нёс валидный nonce | **null** — `invoke` не существовало | null |
| `bound_unused` | есть | есть | **null** — после `bound` не пришло ни одного кадра | null |
| `rejected` | есть | есть | есть, если конверт разобран; иначе null (§5.6) | null — провайдер не вызывался |
| `credential_reflected` | есть | есть | есть | `response_bytes` и `response_body_digest` — **есть**: тело существовало, просто не переслано; digest односторонний и секрета не раскрывает |
| `client_disconnected` | есть | есть | есть — по определению класса `invoke` был принят (§14, R4.2) | `null` — ответ не был отправлен полностью |
| исходы класса A | есть | есть | есть | по таблицам `response_body_digest` / `response_bytes` ниже |

Правило, из которого выведена таблица: **поле имеет значение тогда и только
тогда, когда породившее его событие произошло.** `null` здесь означает «этого не
было», а не «не записали» — та же дисциплина, по которой ниже устроен
`response_body_digest`. Запись, заполняющая поле правдоподобной величиной при
отсутствии события, — это то же ложное свидетельство, что и `digest(b"")` вместо
`null`.

**Preimage каждого digest определён (правка R3).** Хеш без нормативного
preimage — это поле, по которому две корректные реализации получат разные
значения и обе будут правы:

```text
prompt_digest         SHA-256 над ТОЧНЫМИ UTF-8 байтами значения `prompt`
                      после успешного разбора JSON кадра `invoke`
response_body_digest  SHA-256 над ТОЧНЫМИ байтами сырого тела ответа
                      провайдера (см. таблицу ниже)
```

**Поле `schema_digest` удалено (правка R3).** У него не было определённого
preimage, и определить его дёшево нельзя: gate получает `schema` как JSON
value, а не как исходные байты файла, поэтому кандидатов минимум пять — байты
файла (gate их не видит), результат `serde_json`-сериализации, pretty-форма,
форма с отсортированными ключами, JCS/RFC 8785. Семантически одна схема
`{"type":"object","required":["x"]}` и та же схема с другим порядком ключей
дают разные SHA-256. В дереве канонизации JSON, пригодной для произвольного
schema-value, нет: `crates/o7-a1-contracts/src/json.rs` — путь валидации и
допуска (`validate_document`/`parse_artifact`), а не энкодер, и A1-дисциплина
дайджестов работает над **сырыми wire-байтами** конверта, которых здесь не
существует. Тащить JCS в MG-C ради одного диагностического поля — расширение
scope; поле не несёт authority-нагрузки и в M1 просто отсутствует. Если позже
понадобится провенанс схемы, он приходит вместе с нормативной канонизацией,
а не вперёд неё.

**`cap_grant_nonce` — то, что делает выданную authority доказуемой (R2).** Без
него доказательные плоскости не смыкались: SB-B доказывает «запуск X получил
дескриптор `model_invoke`», gate-запись утверждает «соединение Y было связано с
профилем P и моделью M», а поля, доказывающего `X == Y`, не существовало.
`request_id` для этого не годится — его минтит песочница; `gate_invocation_id`
минтит сам gate. Оба доказывают что угодно, кроме соответствия гранту. Поскольку
`CapabilityEvidence` обязана эхоить тот же nonce (`51f97d9…`, Decision 5),
независимый верификатор теперь может сопоставить gate-запись с evidence
конкретного гранта — и отличить «Launch A → reviewer-cheap» от
«Launch B → reviewer-strong», которые на уровне манифеста SB-B неразличимы.

**Соответствие обязано быть однозначным, и равенства nonce для этого мало
(правка R3).** При

```text
CapabilityEvidence:  N → launch X
MG-C audit:          N → reviewer-cheap
                     N → reviewer-strong
```

вопрос «какая authority была у запуска X» остаётся без ответа, хотя все nonce
совпадают. Заморожены **три отдельных обязательства**, каждое у своего
владельца:

```text
SB-B     свежий cap_grant_nonce на каждый грант
         (уже нормативно, Decision 3 — MG-C это НЕ дублирует)

MG-C     каждое соединение, достигшее `bound`, порождает РОВНО ОДНУ
         терминальную audit-запись, несущую связанный с ним nonce —
         включая соединение, которое закрылось, не прислав `invoke`
         (terminal_class = bound_unused)

приёмка  над множеством evidence проверяется БИЕКЦИЯ:
         каждый cap_grant_nonce из CapabilityEvidence ↔ ровно одна
         терминальная MG-C-запись, и наоборот.
         Дубликат, отсутствие или излишек ⇒ evidence set невалиден,
         приёмка fail-closed.
```

`bound_unused` существует именно ради этой биекции: выданная и не
использованная capability — законный исход, и без собственной записи он читался
бы как пропавшее соответствие, то есть как порча evidence.

Полное соответствие исходов классам и участие в биекции (правка R3.1):

| `terminal_class` | достигнутая точка | в биекции |
|---|---|---|
| `bind_rejected` | `bind` не дошёл до `bound` — любой kind групп B1 или B3, сработавший в фазе 1 (§5.6) | **нет** — гранта не существует |
| `bound_unused` | `bound` есть, после него **не пришло ни одного кадра** — соединение закрылось молча | да |
| `rejected` | `bound` есть, провайдер **не вызван** — **любой** kind, сработавший после `bound`: B2/B3 с эхом `request_id`, а также B1 (`malformed_frame`, `unknown_version`, `request_too_large`, `already_bound`) с `request_id: null` (§5.6, уточнено R4.1) | да |
| `client_disconnected` | валидный `invoke` **принят**, клиент исчез до того, как ответ отправлен полностью (§5.7) | да |
| `credential_reflected` | провайдер вызван, тело содержало дословный credential и не переслано (§5.5) | да |
| `http` / `timeout` / `transport` / `redirect` / `too_large` | провайдер вызван, исход из класса A (§5.6) | да |

Класс `rejected` восстановлен именно здесь: отказ после `bound` — законная
трасса (`bound` → `invoke` → источник credential исчез → `rejected`), и без
своего класса такая запись не могла бы существовать, хотя обязательство «ровно
одна терминальная запись на `bound`-соединение» её требует.

**Классы дизъюнктны по построению, а не по правилу приоритета (уточнено
R4.2).** Каждое завершение соединения попадает ровно в один класс, потому что
признаки не пересекаются:

```text
bind не достиг bound                              → bind_rejected
bound достигнут, после него НЕ пришло ни кадра    → bound_unused
кадр пришёл, но валидный invoke НЕ принят         → rejected
валидный invoke принят, клиент исчез до полной
  отправки ответа                                 → client_disconnected
валидный invoke принят, ответ сформирован         → исход класса A
                                                    (включая credential_reflected)
```

Первая редакция R3.1 определяла `client_disconnected` как «клиент исчез», и это
пересекалось сразу с двумя классами: связанный клиент, закрывшийся до `invoke`,
удовлетворял и `bound_unused`, и `client_disconnected`; EOF в середине кадра —
и `rejected`, и `client_disconnected`. При таком перекрытии требование «ровно
одна терминальная запись» неисполнимо: две корректные реализации выберут разные
классы. Сужение `client_disconnected` до фазы «после принятого `invoke`» убирает
оба пересечения без введения приоритетов.

Терминальный класс описывает **состояние gate**, а не то, что получил клиент:
кадр `rejected`, который не удалось отправить исчезнувшему клиенту, всё равно
даёт запись `rejected` — отказ состоялся, доставка отказа к классификации
отношения не имеет.

**Граница `bound_unused` / `rejected` проведена по одному признаку (R4.1):
пришёл ли после `bound` хоть один кадр.** Ни одного — `bound_unused`. Пришёл и
был отвергнут — `rejected`, независимо от группы отвергнувшего kind'а. Это
закрывает трассу, у которой иначе не было бы класса: песочница после `bound`
шлёт malformed-кадр, неизвестную версию, oversize или повторный `bind` — всё это
kind'ы группы B1 (конверт не разобран, `request_id: null`), но происходят они
**после** `bound`, то есть `bind_rejected` (гранта нет) к ним неприменим, а
`bound_unused` (кадров не было) — тоже. Раскладка по группам B1/B2/B3 отвечает
на вопрос «какой `request_id`», а не «какой terminal_class»; смешение этих двух
вопросов и было исходным дефектом, который R4 чинил в §5.6.

Биекция — правило **приёмочного evidence set**, а не структура данных внутри
демона. Gate не хранит множество виденных nonce и не обязан обнаруживать
повтор: повтор со стороны грантов уже является нарушением SB-B, а хранение
lifetime-set вернуло бы ровно ту инфраструктуру, которую три раунда вычищали
(§5.4, §11). До SB-B проверяется более слабое, но исполнимое свойство: два
независимых `bind` с `N1`/`N2` дают две записи, сохраняющие `N1` и `N2` без
перепутывания; настоящая one-to-one проверка живёт в полной вертикали §9.3.

**Правило `response_body_digest` (правка R2).** Поле nullable, и `null` — не
«неизвестно», а «полного тела не существовало»:

| `ArliOutcome` | `response_body_digest` |
|---|---|
| `Http { body }` | `Some(Digest256(body))`, **включая настоящее нулевой длины тело** |
| `TimedOut` | `null` — тело не получено |
| `Transport` | `null` — HTTP-ответа не было |
| `Redirect` | `null` — вариант несёт только `detail`; 3xx, вернувший тело, попадает в `Http` и хешируется там (`e42dc1d…`) |
| `TooLarge` | `null` — полное тело не принято и намеренно не сохранено |
| `Http { body }`, статус не 2xx | `Some(Digest256(body))` — тело получено полностью; в песочницу не переслано, но на доверенной стороне это улика (§5.5, R5) |
| `Http { body }`, отражение credential | `Some(Digest256(body))` — тело получено полностью, но не переслано (§5.5) |

**`response_bytes` следует ровно тому же правилу (правка R3):** `Some(len(body))`
для `Http`, включая `0` у настоящего пустого тела, и `null` для
`TimedOut`/`Transport`/`Redirect`/`TooLarge`. Иначе поле «размер тела ответа»
пришлось бы заполнять у `TooLarge` выдумкой — нулём, лимитом или числом
прочитанных до отказа байт, — и каждый вариант притворялся бы знанием размера
полного ответа, которого gate не получил. Если однажды понадобится «сколько
успели увидеть до отказа», это **другое** поле (`observed_response_bytes`),
вводимое отдельным решением, а не переопределение смысла этого. В M1 его нет.

Безусловное хеширование сделало бы `digest(b"")` одновременно ответом на
«провайдер вернул пустое тело» и на «тела не существовало» — два разных
доказательных утверждения с одним значением. Вместе `terminal_class` и
`response_body_digest` отвечают на вопрос «существовало ли полное тело и какие
у него байты» однозначно.

**Важно не спутать две разные границы (уточнено R5.1):** `response_body_digest`
отвечает на вопрос «существовало ли **физически** полное тело», а не «переслали
ли его в песочницу». Поэтому у non-2xx-ответа с телом digest **есть**, хотя
песочнице тело не ушло (§5.5). Аналогия с `stdout.raw` здесь ограниченная и
раньше была сформулирована неверно: по амендменту `752dd76…` `stdout.raw` пуст
не только для transport- и over-limit-исходов, но и **для всякого non-2xx**.
Совпадение между ним и `response_body_digest` заканчивается на первом вопросе;
второй у них разный, и правило digest'а выведено из таблицы `ArliOutcome` выше,
а не из поведения `stdout.raw`.

**Поля `usage` (токены) в M1 нет — удалено правкой R1.** Первая редакция
разрешала опционально извлечь `prompt_tokens`/`completion_tokens`/
`total_tokens`, и это прямо противоречило принципу §5.5: единственный способ их
получить — распарсить тело ответа провайдера, то есть сделать ровно то, чего
gate делать не должен. «Не интерпретируем тело, но чуть-чуть интерпретируем» —
это второй provider-parser, входящий через служебную дверь. Провенанс ответа
обеспечивается его digest'ом, а не разбором. Извлечение provider-метаданных —
отдельный будущий контракт (`MG-C vNext: provider metadata extraction`) со
своей схемой и с доказательством, что это парсер метаданных, а не второй
классификатор ответа.

Словарь идентичности переиспользуется, а не изобретается: `Digest256`
(`dbd75ec…`) — валидируемый newtype на untrusted-пути, семантически подходит.
`provider_execution_id`/`dispatch_id` из A1-F (`3b26849…`) **не переиспользуются**:
это замороженная грань A1-receipt'ов, и притягивать её сюда означало бы вварить
MG-C в A1-семантику без требования замороженного контракта.

**Не записывается никогда:** текст prompt'а; тело ответа модели; credential;
заголовок `Authorization`; путь к файлу credential; любой материал ключа.
Хранение prompt/ответа «для удобства аудита» прямо запрещено.

Формат и место хранения audit-записей — **отложенное решение** реализующего
среза: он обязан сначала проверить, покрывает ли существующая run-record/ledger
конвенция этот случай, и только при доказанном несовпадении заводить своё.

## 16. Корректирующие раунды

Конвенция репозитория: раунды записываются в самом контракте (как §9
`a1-authority-contracts.md` несёт все семь своих), forward-only — предыдущая
редакция не переписывается задним числом.

### R1 — пять дефектов wire/authority-контракта (внешнее ревью первой редакции)

Первая редакция (`43c1e0e`) имела правильный scope и дисциплину, но содержала
пять load-bearing дефектов. Два — authority/security.

| № | класс | дефект | разрешение |
|---|---|---|---|
| 1 | **P0, authority** | `invocation_profile` выбирал sandboxed caller, gate лишь проверял существование имени. Одна generic `model_invoke` capability давала authority на **все** известные профили; записанный инвариант «профиль не расширяет capability» был декларацией без механизма | профиль **привязан к соединению** в доверенной фазе `bind` до передачи дескриптора; поля нет в кадре `invoke`; `already_bound`/`bind_required` — §5.5, §5.8, §6 |
| 2 | P1, authority | endpoint был заморожен дважды несовместимо: §6 разрешал endpoint внутри профиля, §7 наследовал compile-time константу. Профиль с endpoint расширяет поверхность перенаправления credential | `provider` и `endpoint` — compile-time, из профиля удалены; профиль несёт только `model`, `upstream_timeout`, `credential_source_id` — §6, §7 (последнее поле снято R2) |
| 3 | P1, корректность | грамматика требовала `request_id: "<эхо>"` в каждом ответе, но `request_too_large` обязан детектироваться по префиксу длины — до чтения любого `request_id`. Контракт требовал сериализовать несуществующее значение | `type: "rejected"`, `request_id: string \| null`; таксономия разделена на pre-envelope B1 (`null`, терминально) и post-envelope B2 (эхо) — §5.5, §5.6 |
| 4 | P1, целостность | аудит опционально извлекал `usage`-токены, что достижимо только разбором тела ответа — прямое противоречие принципу «gate не интерпретирует provider body» | `usage` удалён; провенанс через `response_body_digest`; извлечение метаданных вынесено в `MG-C vNext` — §14 |
| 5 | P1, authority | «соединение обслуживает произвольное число последовательных вызовов» бесплатно выдавало неограниченную модельную/вычислительную authority из одного гранта; ни один потребитель этого не просил | capability **single-shot**: bind → один `invoke` → ответ → close — §5.4 |

Дополнительно ослаблено до честной формы: требование «прервать незавершённый
upstream-вызов» при разрыве клиента (§5.7). Существующий `invoke_arliai::call`
(`e42dc1d…`) синхронен и не отдаёт cancellation handle, то есть сильная форма
была новым транспортным требованием, записанным как данность. Заморожена
bounded-форма (результат отброшен, retry нет, upstream ограничен доверенным
таймаутом); сильная форма — отложенное решение, принимаемое только вместе с
доказательством прерываемости.

Что R1 **не** менял: blob-pinning, таблица состояния пререквизитов, граница
SB-B/MG-C, возврат сырого тела вместо второго `classify_arli`, отсутствие FIFO,
стриминг как non-goal, credential-поправка под ратификацию, call-scoped время
жизни секрета, разделение SB-owned/MG-C-owned приёмки, socketpair как
gate-only шов, отказ тащить A1-идентификаторы в аудит.

### R2 — три коррекции, вскрывшиеся после закрытия P0 первого раунда

R1 закрыл runtime-authority. После этого стало видно, что доказуемость
выданной authority и резидентность секрета остались незакрытыми.

| № | класс | дефект | разрешение |
|---|---|---|---|
| 1 | **P0, credential** | §8.3 запрещала резидентное владение секретом, а §8.4 разрешала для разработки окружение процесса. Для долгоживущего демона это то же самое резидентное владение: значение лежит в `/proc/<pid>/environ` весь срок жизни, наследуется потомками, попадает в core dump. Документ противоречил сам себе через один раздел | provider-credential в окружении gate **запрещён в любом режиме**; источник M1 — доверенный файл/дескриптор вне адресного пространства между вызовами; gate **отказывается стартовать**, обнаружив credential в своём окружении; `credential_source_id` убран из профиля — §8.4, §6 |
| 2 | P1, доказуемость | профиль был привязан к сокету в рантайме, но не к гранту в доказательной плоскости. SB-B доказывает «запуск X получил `model_invoke`», gate — «соединение Y имело профиль P»; поля, доказывающего `X == Y`, не было. ### R3 — доказательная гигиена: кардинальность, preimage, отсутствующие значения

R2 ввёл корреляцию грант↔запись. R3 закрывает три места, где эта корреляция и
соседние поля обещали больше определённости, чем несли.

| № | класс | дефект | разрешение |
|---|---|---|---|
| 1 | P1, доказуемость | «верификатор может сопоставить запись с грантом» требует не только равенства nonce, но и **кардинальности**: при двух записях с одним nonce вопрос «какая authority была у запуска X» остаётся без ответа | биекция как правило **приёмочного evidence set**, а не как структура в демоне: свежесть nonce остаётся за SB-B, «ровно одна терминальная запись на `bound`-соединение» — за MG-C, one-to-one проверка — за приёмкой; введён `bound_unused`, чтобы законно неиспользованная capability не читалась как пропавшее соответствие; `bind_rejected` исключён из биекции по определению — §14 |
| 2 | P1, определённость | `schema_digest` не имел нормативного preimage: gate видит `schema` как JSON value, а не байты файла, и пять способов кодирования дают пять разных SHA-256 при одной семантике. Две корректные реализации разошлись бы, обе соответствуя контракту | поле **удалено** из M1 (authority-нагрузки не несёт); канонизации, пригодной для произвольного schema-value, в дереве нет — `o7-a1-contracts/src/json.rs` — путь валидации/допуска, а не энкодер; `prompt_digest` определён как SHA-256 над точными UTF-8 байтами значения после разбора кадра — §14 |
| 3 | P1, определённость | `response_bytes` был безусловным «размером тела ответа», хотя у `TooLarge`/`TimedOut`/`Transport`/`Redirect` полного тела не существует; заполнение нулём, лимитом или числом прочитанных байт притворялось бы знанием размера полного ответа | `u64 \| null` по той же таблице, что `response_body_digest`; «сколько успели увидеть» — отдельное будущее поле `observed_response_bytes`, а не переопределение смысла этого — §14 |

Дополнительно `cap_grant_nonce` **повышен в статусе**: из «предположения,
подлежащего проверке» — в **version-sensitive upstream dependency** с явным
правилом инвалидации (§13). MG-C v1 нормативно требует от выбранной версии SB-B
стабильную per-grant correlation identity, доступную launcher'у до CAP_GRANT и
присутствующую в `CapabilityEvidence`; на blob'е `51f97d9…` это
`cap_grant_nonce`. Смена идентичности в SB-B допустима, но запускает
compatibility gate и отдельный supersede round, а не правку названия поля.
Альтернатива — протащить profile/model в манифест SB-B — отвергнута как
архитектурный регресс: транспорт снова знал бы, зачем используется capability.

Что R3 **не** менял: ничего из R1/R2. Все правки — в §13 и §14 плюс четыре
строки матрицы §9.2.

### R5 — граница по HTTP-семантике вместо остаточного риска (решение мейнтейнера)

Третий проход Codex настаивал, что признание преобразованного отражения
(`base64(credential)`) остаточным риском само по себе нарушает центральное
заявление репозитория. Класс дефекта назван верно, но буквальное требование —
«не пересылать представление, способное нести credential» — невыполнимо: адресат
bearer-токена может вернуть произвольные байты, и список энкодеров бесконечен.
Решение мейнтейнера: провести границу по **HTTP-семантике**, а не фильтрацией.

| что | решение |
|---|---|
| non-2xx (diagnostic channel) | тело **никогда** не пересекает границу песочницы; вызывающий классифицирует по статусу — `classify_arli` и так читает только статус |
| 2xx (model-output channel) | сырое тело пересылается: по нему работает существующий классификатор и локальная schema-валидация. Containment-проверка на дословный credential сохраняется как defense in depth |
| `credential_reflected` | сужен до 2xx: на non-2xx тело запрещено безусловно, и превращать честный `401` в `credential_reflected` значило бы потерять основную классификацию |
| модель угроз | §8.6: M1 **не** обещает confidentiality против злонамеренного/скомпрометированного провайдера. Провайдер — доверенный получатель credential; 2xx model output — явный declassification channel |

**Дефект оказался шире MG-C.** `AGENTS.md` (правило 1) считает P0 и косвенный
путь — запись вывода провайдера в run record без учёта того, что он мог отразить.
При этом существующий прямой путь `--engine arliai` сохраняет **любое** in-bound
тело в `stdout.raw`, включая diagnostic. То есть поверхность, которую MG-C
запрещает у gate, уже открыта в реализованном пути.

Поэтому правило исправлено **уровнем выше**, а не исключением внутри MG-C: в
`docs/o7-invoke.md` внесена поправка «non-2xx body не является canonical run
evidence», MG-C наследует её и перепинен на новый blob
(`752dd76…`). Второй, расходящейся evidence-семантики «через gate не совсем
raw» не заводится.

**Открытое следствие:** реализация `run_arliai` поправке ещё не соответствует —
контракт исправлен первым, намеренно. Пока это так, §8 **не готова к
ратификации**: ужесточать credential-границу для нового процесса, оставляя ту же
поверхность в старом, было бы половиной работы. Порядок зафиксирован в §8.2.

Что R5 **не** менял: raw relay для 2xx, single-shot, двухфазную привязку,
таксономию B1/B2/B3, дизъюнктность терминальных классов, биекцию evidence.

### R5.1 — две несогласованности, оставленные самим R5

| № | класс | дефект | разрешение |
|---|---|---|---|
| 1 | **P0, формулировка гарантии** | §8.5 сохраняла категорический список «credential не виден песочнице ни через … RPC (запрос или **ответ**)», хотя §8.6 объявляет 2xx model output declassification-каналом и блокирует только дословное вхождение. Правило digest'а выведено из таблицы `ArliOutcome`, а не из поведения `stdout.raw` — §14 |

| № | класс | дефект | разрешение |
|---|---|---|---|
| 1 | P1, дрейф | блок §5.5 «граница проведена по HTTP-семантике» **нормативно пересказывал** границу модели угроз — non-2xx не пересекает границу, 2xx пересылается, блокируется только дословное вхождение — не ссылаясь на §8.6. Будущая правка §8.6 оставила бы §5.5 с более сильным или устаревшим правилом: ровно тот механизм дрейфа, против которого R5.2 и вводил правило | §5.5 явно ограничен **механикой** («что делает gate») и открывается ссылкой на §8.6 как на источник границы гарантии, со старшинством §8.6 при расхождении; формулировки про силу обещания (defense in depth, где кончается гарантия) убраны из §5.5 и оставлены только в §8.6 |

Отдельно подтверждено тем же проходом: пять условий приёмки §9.3 совместно
проверяемы и не требуют отвергать 2xx-тело, содержащее преобразованный
credential, — то есть исправление R5.2 в §9.3 держится.

Дефект стоит записи не из-за размера правки, а из-за того, что он показывает:
правило единственного места не выполняется само собой. Оно требует, чтобы при
каждой правке §8.6 кто-то прошёл по ссылающимся разделам — иначе через два
раунда снова появится независимая формулировка.

**Структурная правка, чтобы это не повторилось в четвёртый раз.** В §8.6
введено *правило единственного места*: граница модели угроз определяется там и
только там, остальные разделы обязаны на неё **ссылаться**, а не пересказывать.
Три раунда подряд ловили одну и ту же механику — правило меняется в одном
разделе, прежняя формулировка остаётся в другом (§8.5 в R5.1, §3 и §9.3 в
R5.2). Пересказ гарантии в N местах — это N мест, которые разойдутся при
следующей правке; ссылка расходиться не умеет.

Обе — про то же самое: R5 менял правило в одном месте и оставлял его прежнюю
формулировку в другом. Первая нашлась бы только внешним ревью, вторая —
следствие механической правки ссылок, которая выглядит безопасной ровно до
момента, когда текст рядом с ссылкой описывает старое правило.
