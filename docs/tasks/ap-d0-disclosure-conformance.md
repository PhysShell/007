# AP-D0: external disclosure conformance — prior art, отложено

Статус: **DEFERRED — consumer отсутствует.** Не предложение, не контракт, не
разрешение на реализацию. Ни spec, ни RED-harness по этому документу не
пишется до срабатывания триггера §1.

```text
реальная проблема 007        trustworthy execution provenance
                             (какой прогон, над каким состоянием, с какими
                              входами, какой выход, доказуемая связь)

проблема этого документа     interoperability этого provenance с внешними
                             disclosure-инструментами

сегодня                      второе — решение без потребителя
```

Документ существует по двум причинам: результаты проверки первоисточников
(§3) стоили работы и не должны переоткрываться, и когда/если потребитель
появится, форма работы уже известна (§5) — но именно как *форма*, а не как
задание.

## 1. Условие активации

Активируется при **любом** из событий, не раньше:

```text
T1  появился внешний потребитель раскрытия: организационная политика,
    supply-chain / governance scanner, compliance-аудит, downstream tooling,
    которому наши коммиты подаются на вход
T2  007 публично обещает машинно-детектируемое AI-provenance, совместимое
    с внешним инструментарием — обещание без свидетеля есть болтовня
T3  merge/release gate или verification pipeline начинает читать раскрытие
```

Ни одно из трёх сегодня не выполнено. Проверено на момент записи: GitHub
ничего такого не требует, наш verification pipeline раскрытие не читает,
пользователь 007 его не видит, downstream-потребителя нет.

**Ложный триггер.** «Мы обнаружили, что раскрытие сломалось» триггером **не
является**, пока никто его не читает. Сломанное раскрытие без потребителя —
это не отказ, это отсутствие функции.

**Проблема самой отсрочки.** Отложенные документы гниют: условие активации
проверяет тот, кто на него наткнётся, а наткнуться он должен там, где триггер
наблюдается, — в `README.md` / `docs/public-governance.md` (T2), не в
`docs/tasks/`. Перекрёстная ссылка не проставлена намеренно: ставить её
означало бы редактировать публичные документы ради гипотезы. Если T2 когда-то
станет обсуждаемым, ссылка ставится тогда. Прецедент, почему это важно, —
`docs/tasks/mg-c-model-gate.md`, где заголовок «▶ RESUME HERE» в `TODO.md`
читается как инструкция, будучи историей, и сам документ называет это дефектом
читаемости.

## 2. Что уже верно без всякой работы

167 из последних 200 коммитов этого репозитория несут
`Co-Authored-By: Claude`. При этом `o7` не эмитит ничего: в `src/` и
`crates/` нет кода, порождающего трейлер. Проверено на ревизии `b712455`.

```text
CHAOSS-детектируемое раскрытие у 007 уже существует
источник                 дефолт Claude Code
наше участие             отсутствует
следовательно            строить нечего — только наблюдать
```

Отсюда два следствия, оба в пользу отсрочки. Шаг «определить одну producer
disclosure form» беспредметен: форма зафиксирована чужим дефолтом. Свидетель
проверял бы свойство, получаемое даром.

И одно возражение, которое не отменяет отсрочку, но должно быть записано:
свойство держится на чужом дефолте и может исчезнуть молча — тот же класс
отказа, что зафиксирован для детектора в §3 F6, только со стороны эмиссии.
Это станет существенным ровно тогда, когда сработает триггер §1, и ни днём
раньше.

## 3. Проверенные факты (единственная durable часть)

Установлены чтением исходников, не README. Разделение artifact-says /
inference — `docs/evidence-and-decision-discipline.md` правило 4. Ревизии на
2026-08-11:

```text
andrew/critical-ai-scan   8e7d0c19a66b647ff071b37bd4531e02562cb1c9   MIT
chaoss/disclosure  (pin)  8c01a4374f52696a0a9aae8c55dd6ab2df71250c   2026-07-30
chaoss/disclosure  (HEAD) 8e6b05425c0f9a290d94958865484ba342b81e9d   2026-08-06
                                                                    GPL-3.0
```

**F1 — `signal` не является полем CHAOSS.** Публичный `detection.Finding`
несёт только `detector`, `tool`, `model`, `confidence`, `detail`
(`detection/detection.go:35`). Таксономия `agent_identity / coauthored /
assisted_trailer / tool_attribution / tool_mention` — собственная структура
`critical-ai-scan` (`stream.go:30`), выводимая `signalKind()`
(`stream.go:467`) по **префиксам прозаического `Detail`**.
*Вывод:* связка ломается молча при переформулировке человекочитаемой строки
в upstream. Любая проверка, опирающаяся на `detail`, наследует эту хрупкость.

**F2 — `explicitAITool()` содержит 36 фрагментов** (`stream.go:619`),
матчинг `strings.Contains` плюс `containsASCIIWord(normalized, "ai")`.
*Вывод:* подстрочные ложноположительные возможны (`"opus" ⊂ "octopus"`,
`"trae" ⊂ "traefik"`), но применяются только к полю `Tool` разобранного
`Assisted-By` — риск низкий. Существенный дефект другой: отсутствуют `llama`,
`mistral`, `windsurf`, `cline`, `continue`, `cody`, `tabnine`, тогда как
Windsurf, Cline и Continue **инвентаризируются** тем же проектом на уровне
instruction files. Асимметрия между двумя поверхностями одного сканера.

**F3 — знаменатель 353/5682 корректен.**
`data/critical-github-instructions.json`: `repositories_scanned: 5682`,
`repositories_with_files: 353`, `repository_share: 0.06212601196761704`.
Прозаическое «examined 5,707 repositories» в README расходится с данными
самого проекта; данные авторитетнее.

**F4 — агрегаты.** `data/critical-github-summary.json`: `commits 589798`,
`validated 17279`, `share 0.029296…`, `h1_2026 0.041251…`,
`repositories_with_commits 3533`, `repositories_with_validated_signals 687`.
Разбивка: `coauthored 10417`, `autonomous 4651`,
`validated_assisted_trailer 2212`, `tool_attribution 66`.
*Вывод:* «рост declared assistance» — на 84 % один канал, `Co-Authored-By`.

**F5 — прибор ýже детектора.** `methodology.git_notes: "not fetched"`, при том
что детектор `detection/gitnotes` существует и `refs/notes/ai` относится к
high confidence.

**F6 — дрейф детектора за 7 дней.** Между пином и HEAD 26 коммитов, 4 в
`detection/`. Существенный — `56958c5 Detect AI agent authors and committers`:
расщепляет `detection.Input.CommitEmail` на `AuthorEmail` + `CommitEmail`,
после чего committer-детектор срабатывает и по автору — строгое расширение
`agent_identity`. Прирост `constants.go` (+82) ушёл в
`SupportedToolsInMentions`; `KnownAgentCommitters` не изменилась.
*Вывод:* тот же корпус под HEAD даст строго больший autonomous-счёт;
опубликованные числа воспроизводимы только под пином и именно поэтому
несопоставимы с будущими. Побочно: семантика полей публичной структуры
изменилась за неделю — библиотечный API upstream нестабилен.

**F7 — метрология внешнего исследования.** Измеряется
`observed_rate = usage × P(disclosure | tool, policy, time)`; оба сомножителя
нестационарны (F4, F6). Знаменатель — default-branch non-merge commits —
несопоставим между организациями с разной merge policy; squash является
каналом потери **или преобразования** раскрытия, а не гарантированного
стирания. Размеченной подвыборки нет нигде, поэтому precision/recall детектора
на диком корпусе неизвестны. Дельта pinned→current измеряет чувствительность
к версии детектора и **не является** оценкой recall.

## 4. Чего conformance-witness не закрыл бы даже зелёным

Записано, потому что это и есть граница между настоящей задачей и этой.
Зелёный внешний скан утверждает ровно одно: в коммите есть узнаваемая
табличка. Он молчит про:

```text
какой конкретный прогон породил этот коммит
какой был base_commit и совпадает ли он с заявленным
какие инструкции фактически действовали
какая версия модели
какой выход относится к какому выполнению
не подменена ли запись
соответствует ли коммит результатам прогона
цела ли цепочка execution → artifact
```

Разница между бейджиком посетителя и цепочкой custody. Настоящая задача 007 —
вторая. Эта — первая.

## 5. Форма работы, если триггер сработает (ненормативно)

Не задание. Записано, чтобы не переоткрывать конструкцию.

Два раздельных свидетеля — слияние их дефектно, так как squash в чужом
репозитории уронил бы producer-инвариант при корректном producer'е:

```text
W1  producer-output-conformance
    прогон агента → коммит → внешний сканер видит ожидаемое раскрытие
W2  merged-output-survival
    коммит / PR → merge policy → default-branch коммит всё ещё несёт раскрытие
```

Утверждение — **равенство множеств findings после проекции**, не наличие.
Exit code как свидетель непригоден: `1` означает «что-нибудь сработало».
Проекция по `detector`, `confidence`, `tool`, `model`; поле `detail`
исключено (F1). Собственная таксономия `signal` не вводится — она потребовала
бы воспроизвести разбор прозы. Форма вывода `disclosure scan --format=json`
(`scan/scan.go:10-25` пина):

```json
{ "commits": [ { "hash": "…", "findings": [ { "detector": "…", "tool": "…",
                 "model": "…", "confidence": "high", "detail": "…" } ] } ],
  "summary": { "total_commits": 0, "ai_commits": 0,
               "tool_counts": {}, "by_confidence": {} } }
```

Минимум — один известно-положительный и один известно-отрицательный фикстур;
без второго проверка не отличима от всегда-зелёной.

Precision/recall, если понадобятся, меряются на **producer-known корпусе** и
только по нашему диалекту раскрытия. Это не оценка recall CHAOSS на диком
корпусе, и цитировать её так нельзя.

## 6. Лицензионная граница (действует независимо от статуса)

`critical-ai-scan/go.mod` содержит прямой
`require github.com/chaoss/disclosure v0.0.0-20260730124854-8c01a4374f52`;
`chaoss/disclosure` — GPL-3.0. Go линкуется статически; позиция FSF: при
**распространении** связанный бинарь образует combined work. MIT на
собственные исходники Andrew этому не противоречит и этого не отменяет.

```text
приемлемо        exec отдельного процесса, обмен argv/stdout/JSON,
                 локальная сборка из upstream-исходников
вне рассмотрения импорт Go-модуля, вендоринг, раздача собранного бинаря
не утверждается  что «отдельный процесс» снимает вопрос автоматически:
                 FSF формулирует это как «обычно, но важна семантика
                 взаимодействия», и FAQ не является судебным решением
неочевидно       flake input сам по себе distribution не образует, если
                 указывает, откуда получить GPL-исходники; раздача
                 собранного артефакта — образует
```

Собственная реализация детекторов не рассматривается: смысл конструкции — в
**независимости** парсера от нас. Списки идентичностей — факты и вряд ли
охраноспособны, но копирование файла списка из GPL-репозитория остаётся
копированием.

## 7. Что зафиксировано как решённое

Чтобы не переоткрывать в третий раз:

- `docs/ai-provenance.md` **не создаётся**;
- «AI involvement» как inference не строится ни в каком виде — 007 producer,
  ground truth известен в момент выполнения;
- четырёхсостояний `observed → validated → policy-relevant → enforced` не
  вводится; при необходимости — три независимых объекта без переходов:
  `Observation` (неизменяемое свидетельство) ≠ `ValidationPolicy`
  (версионированный предикат) ≠ `PolicyBinding` (потребитель + следствие);
- норма «наблюдение не подразумевает вердикт» — **non-goal**, не запись
  реестра: нет enforcement site и нет краснеющего свидетеля. Enforceable-
  остаток, если схема когда-либо появится: запись не содержит нормативных
  полей (`verdict`, `trust`, `correctness`, `policy_status`,
  `authorship_fraction`, `risk_score`), а решение политики ссылается на
  наблюдение только через типизированный binding — второе получает свидетеля
  в виде negative-compilation probe;
- слово «reproducibility» к запускам агента неприменимо: достижимо
  **attributability**;
- статический обход `AGENTS.md`/`CLAUDE.md` не даёт effective instruction set
  (precedence — свойство бинаря агента; плюс system prompt, флаги CLI,
  `@`-импорты, user-level память, skills, plugins, описания MCP-тулов).
  Полезная конструкция — пара EXPECTED / OBSERVED с расхождением дайджестов
  как свидетельством, и она реализуема только если OBSERVED вообще наблюдаем
  через внешний CLI. Не проверено. Это вопрос настоящей provenance-задачи
  (§4), а не этого документа.
